# Faults, Watchdog, Power: the Crash Lab
## SOC3050 ARM Edition — Part 2, Systems

**Reference**: [STM32 Reference Manual](https://www.st.com/resource/en/reference_manual/rm0490-stm32c0x1-advanced-armbased-32bit-mcus-stmicroelectronics.pdf) ·
**Board manual**: [UM2953, STM32 Nucleo-64 boards (MB1717)](https://www.st.com/resource/en/user_manual/um2953-stm32c0-nucleo64-board-mb1717-stmicroelectronics.pdf)

**Crash it on purpose — then make it survive.**

Every program you have written so far assumed it would keep running. Real
products do not get that luxury: a wild pointer, a stack that grows one call
too deep, a loop that waits for an event that never comes. This lesson's
firmware is a **crash lab**: a menu of fourteen deliberate failures, a
HardFault reporter that writes a flight record into RAM that **survives the
reset**, a decoder that turns that record into a verdict, and a watchdog that
brings back a system that hangs — or one that only *looks* alive.

Figures marked **measured on the host** come from `host/test.c`, compiled with
plain gcc on a PC (slide 28 says exactly what). Instruction listings are read
out of this lesson's own `Main.elf`. Nothing here has been watched running in
Wokwi yet.

## The Board: This Lesson's Pins

Before any register, find the pins. Every highlighted dot is a header pin that
this lesson's `diagram.json` wires something to — the same circuit you paste
into Wokwi — at its position on the Nucleo-C031C6, to scale. A label reads
*MCU pin (header name, if different)* and what the pin does here.

The two outer double rows are ST's **morpho** headers, which reach every pin
of the chip; the two inner single rows are the **Arduino**-compatible header
(A0–A5 on the left, D0–D15 on the right). Some MCU pins appear on both — PA5 is
also `D13` — so the highlighted position is the one this lesson's wire uses.
The real board's headers are drawn in its manual, UM2953 (top bar).

slide 4). Each cell below is one pin, drawn in register order, marked with how
this lesson configures it.

## Slide 3: One Handler, No Reasons

| | Cortex-M0+ (this chip, Armv6-M) | Cortex-M3/M4/M7 (Armv7-M) |
|---|---|---|
| fault exceptions | **HardFault only** | HardFault, MemManage, BusFault, UsageFault |
| "why" register | **none** | `CFSR`, `HFSR` |
| "where" for a data fault | **none** | `MMFAR`, `BFAR` |
| unaligned word/halfword access | **always faults** | allowed (optional trap) |
| divide by zero | **no divide instruction** | `SDIV`/`UDIV`, optional trap |
| stack limit register | none | none (`MSPLIM` arrives in Armv8-M) |

That table is checked against CMSIS: `core_cm0plus.h` contains no `CFSR`,
`HFSR`, `MMFAR` or `BFAR` at all; `core_cm4.h` has all four.

*why*". This lesson runs on the M0+ instead (the syllabus's F446RE is not
available in this course's simulator), so it does what you must do on every
M0+ product: **reconstruct the why from the evidence.**

## Slide 5: The Evidence, Decoded

Two words in the frame matter before any instruction is read:

```regs
# Stacked xPSR (flags N Z C V vary), and the two EXC_RETURN values of a thread
xPSR ; normal: T = 1, thread mode | 32 = 0x01000000 | 31 N, 30 Z, 29 C, 28 V, !24 T, 9 pad, 5:0 ISR
xPSR ; after the NULL call: T clear | 32 = 0x00000000 | 31 N, 30 Z, 29 C, 28 V, !24 T, 9 pad, 5:0 ISR
EXC_RETURN ; this lesson: main stack | 32 = 0xFFFFFFF9 | 31:4 all ones, !3 Thread, !2 PSP, 1:0
EXC_RETURN ; lesson 07: a task faulted | 32 = 0xFFFFFFFD | 31:4 all ones, !3 Thread, !2 PSP, 1:0
```

- **`T` = 0** means something branched to an **even** address. Every
  Cortex-M instruction is Thumb; the core cannot leave Thumb state, so the
  next instruction faults. The pc is then the branch *target*, and lr still
  points just past the call.
- **`ISR`** non-zero means the fault was inside an interrupt handler.
- **bit 9** says the hardware inserted a padding word to align the stack to
  8 bytes, so the faulting code's sp was frame + 32 **+ 4**.
- **`EXC_RETURN` bit 2** picks the stack the frame is on. This lesson has no
  RTOS, so it is always MSP; the handler checks anyway, so it works under
  lesson 07's kernel unchanged.

## Slide 6: The Handler — Save First, Think Later

```c
__attribute__((naked)) void HardFault_Handler(void)
{
    __asm volatile(
        "   ldr   r3, =crash_hi      \n"
        "   stmia r3!, {r4-r7}       \n"     /* r4..r7                         */
        "   mov   r4, r8             \n"
        "   mov   r5, r9             \n"
        "   mov   r6, r10            \n"
        "   mov   r7, r11            \n"
        "   stmia r3!, {r4-r7}       \n"     /* r8..r11                        */
        "   movs  r0, #4             \n"
        "   mov   r1, lr             \n"
        "   tst   r0, r1             \n"     /* EXC_RETURN bit 2: which stack? */
        "   beq   1f                 \n"
        "   mrs   r0, psp            \n"
        "   b     2f                 \n"
        "1: mrs   r0, msp            \n"
        "2: mov   r1, lr             \n"     /* arg 2: EXC_RETURN              */
        "   ldr   r2, =crash_from_hardfault \n"
        "   bx    r2                 \n"
```

- **`naked`**: no compiler prologue, so nothing has moved before the first
  instruction. r0–r3 can be used freely — their values are safe in the frame.
- Thumb-1 can only `stmia` the **low** registers, so r8–r11 travel down
  through r4–r7 after those are saved — lesson 07, slide 7's trick again.
- Then `crash_from_hardfault(frame, exc_return)` copies everything into the
  flight record, reads the halfword at the stacked pc, prints **one line with
  no `printf`**, and resets the chip (slide 13).

## Slide 7: Reading the Instruction at pc

The stacked pc points at the culprit. `diag.c` reads the halfword there and
recognises every Armv6-M form that can fault:

| Encoding (hw) | Instruction | Address it touched |
|---|---|---|
| `0110 1 imm5 Rn Rt` | `ldr Rt, [Rn, #imm5*4]` | Rn + imm×4 |
| `0111 1 …` / `1000 1 …` | `ldrb` / `ldrh` | Rn + imm, Rn + imm×2 |
| `0101 opc Rm Rn Rt` | `str strh strb ldrsb ldr ldrh ldrb ldrsh` | Rn + Rm |
| `1001 L Rt imm8` | `ldr/str Rt, [sp, #imm8*4]` | sp + imm×4 |
| `01001 Rt imm8` | `ldr Rt, [pc, #imm8*4]` | Align(pc+4, 4) + imm×4 |
| `1011 010 M list` / `1011 110 P list` | `push` / `pop` | sp − 4n / sp |
| `1100 L Rn list` | `stmia` / `ldmia` | Rn |
| `0100 0111 L Rm 000` | `bx` / `blx Rm` | — a Thumb-bit suspect |
| `1101 1110 imm8` / `1011 1110 imm8` | `udf` / `bkpt` | — |

Because the instruction did **not** complete, its base registers still hold
the values it used — and `crash_hi` holds r4–r11 — so the address is
**recomputable**. That is the M0+'s substitute for `BFAR`.

**Measured on the host:** the decoder was run over **every 16-bit
instruction objdump finds in `Main.elf`** — 2327 loads, stores, pushes, pops,
`ldm`, `stm`, branches and traps — and printed **the same text as objdump for
all of them, 0 mismatches**.

## Slide 8: The Verdict — Five Questions in Order

```c
if (!(xpsr & (1UL << 24)))          return CAUSE_THUMB_BIT;     /* 1 */
if (!mem_can(pc, 2, MEM_X))         return CAUSE_BAD_FETCH;     /* 2 */
thumb_decode(hw1, hw2, pc, regs, &ins);                         /* 3 */
if (ins is udf / bkpt / svc)        return that;
if (addr & (size - 1))              return CAUSE_UNALIGNED;     /* 4 */
if (!mem_can(addr, span, MEM_R))    return CAUSE_BAD_ADDRESS;
if (store && region is read-only)   return CAUSE_READ_ONLY;     /* 5 */
```

The memory map it checks against — base addresses from `stm32c031xx.h`,
sizes from `link.ld`:

| Region | Range | R | W | X |
|---|---|---|---|---|
| flash (and its alias at 0) | `0x0800_0000` + 32 KB | ✓ | | ✓ |
| system memory | `0x1FFF_0000` | ✓ | | ✓ |
| SRAM | `0x2000_0000` + 12 KB | ✓ | ✓ | ✓ |
| peripherals, GPIO | `0x4000_0000`, `0x5000_0000` | ✓ | ✓ | **never** |
| core private (SCB, NVIC, SysTick) | `0xE000_0000` | ✓ | ✓ | **never** |
| anything else | e.g. `0x6000_0000` | | | |

Peripheral space is **Execute Never** in the Armv6-M default memory map:
fetching code from a register block faults even with the Thumb bit set.

## Slide 9: Fault 1 — Unaligned

```c
a = (uintptr_t)words + 1u;                  /* 1 byte into a word     */
sink = *(volatile uint32_t *)a;             /* LDR: Armv6-M faults    */
```

As compiled (read from `Main.elf`):

```
80016ec:  9b01   ldr  r3, [sp, #4]      @ r3 = 0x2000000D
80016ee:  681a   ldr  r2, [r3, #0]      @ <- stacked pc: HardFault
```

The decoder's verdict, **measured on the host** with those exact bytes and
`r3`: `UNALIGNED ACCESS — 4-byte access to 0x2000000D, which is not a
multiple of 4`.

On a Cortex-M4 the same load simply *works*, a little slower. Code that ran
for years on an M4 can fault the first day on an M0+. Byte accesses
(`ldrb`, `strb`) can never misalign — that case is in the host test too.

**Simulators differ here.** Renode does not fault on unaligned access (the
ARM README records it). Whether Wokwi does is Lab Part 1's first question —
the firmware prints *"this core did NOT fault"* if it gets past the load.

## Slide 10: Faults 2 and 3 — Nothing There, or Read-Only

**A wild pointer** — `*(uint32_t *)0x60000000`. Nothing on the C031 answers
at that address, so the bus returns an error and the load faults. Verdict:
`NOTHING MAPPED THERE`, address `0x60000000` — recomputed from `r3`, the way
`BFAR` would have reported it.

**A store into flash** — `*(uint32_t *)0x08007F00 = 0x12345678`. Flash is
programmed through `FLASH->CR`, a key sequence and a 64-bit write; an ordinary
store is not a program operation. Whether the bus *faults* or the flash
controller merely *refuses and records an error* is not something this lesson
claims. The firmware is written for both:

```regs
# If the store did not fault, these say why the flash refused it
FLASH->SR | 32 | 18 CFGBSY, 16 BSY1, 15 OPTVERR, 14 RDERR, 9 FASTERR, 8 MISERR, !7 PGSERR, 6 SIZERR, 5 PGAERR, !4 WRPERR, !3 PROGERR, 1 OPERR, 0 EOP
```

If it returns, it prints the word read back and `FLASH->SR`. If it faults, the
decoder says `STORE TO READ-ONLY`. Either way, Lab Part 2 writes down which.

## Slide 11: Faults 4 and 5 — Jumping Where Code Is Not

**A NULL callback** — the most common real one. A function pointer that was
never set:

```
8001734:  9301   str  r3, [sp, #4]      @ r3 = 0
8001736:  9b01   ldr  r3, [sp, #4]
8001738:  4798   blx  r3                @ branch to 0x00000000, bit 0 = 0
```

`blx` to an even address clears the Thumb bit, and the very next fetch
faults. The stacked **pc is 0** — useless for `addr2line` — but **lr is
`0x0800173B`**: the return address of the call, one instruction after the
culprit. **The rule: when pc is nonsense, read lr.**

**Into a register block** — the same `blx`, with `RCC | 1`. The Thumb bit is
*set* this time, so `T` stays 1 and the fault is the fetch itself: pc =
`0x40021000`, in peripheral space, Execute Never. Verdict: `BAD INSTRUCTION
FETCH`. lr again points at the call.

Both verdicts **measured on the host** from these exact frames.

## Slide 12: Faults 6 and 7 — and Two Things That Do Not Fault

`udf #11` (`de0b`) is *permanently undefined*: every Arm core faults on it.
Compilers emit it for `__builtin_trap()`. `bkpt` (`be11`) halts the core when
a debugger is attached; with none, Armv6-M escalates it to HardFault — so a
stray breakpoint left in production code resets the product.

**Reading address 0 does not fault** on this chip. Address 0 aliases the boot
flash, and word 0 of flash is the vector table's initial stack pointer:
`*(uint32_t *)0` reads `0x20003000`, `&_estack`. A NULL *read* on an STM32
returns a plausible number — the worst kind of bug.

**Dividing by zero does not fault** either. The M0+ has no divide
instruction; `100 / zero` is a call to libgcc's `__divsi3`. Traced by hand
through this build's listing: a zero divisor reaches

```
800039e:  b501   push {r0, lr}
80003a0:  2000   movs r0, #0
80003a2:  f000   bl   80003b0 <__aeabi_idiv0>     @ 80003b0: 4770  bx lr
80003a6:  bd02   pop  {r1, pc}
```

and returns **0**. No trap, no flag — unless you define your own
`__aeabi_idiv0` (it is weak). Lab Part 3 checks the 0.

## Slide 14: Why Did We Reset? Two Witnesses

The chip's witness is `RCC->CSR2`: a flag per reset source, sticky until
software clears them all at once with `RMVF`.

```regs
RCC->CSR2 ; read once at boot, then RMVF | 32 | !31 LPWR, !30 WWDG, !29 IWDG, !28 SFT, !27 PWR, !26 PIN, !25 OBL, !23 RMVF, 1 LSIRDY, 0 LSION
```

(Each shaded flag is `RCC_CSR2_xxxRSTF` in `stm32c031xx.h`; `diag.h` keeps a
copy for the host, and `Main.c` checks every one with `_Static_assert`.)

The firmware's own witness is `crash_rec.reset_why`, written just before every
reset it asks for: *HardFault reporter*, *stack canary*, *soft watchdog*,
*reset command*. `RCC` can only say "software"; this says **which** software.

The second witness matters here: Wokwi lists its **RCC model as partial**. If
`CSR2` reads all zeros after a reset — impossible on silicon, where power-on
alone sets `PWRRSTF` — the boot report says *"this simulator does not model
them"* and relies on `.noinit` alone.

## Slide 15: Stack Overflow — Nothing Faults

The main stack grows down from `0x20003000` toward the heap. Nothing stops
it: there is no stack-limit register on Armv6-M, and memory below the floor is
ordinary RAM — **legal to write**. An overflow does not fault; it silently
rewrites the heap, then `.noinit`, then `.bss`.

So `main()` first **paints** the stack with `0xDEADBEEF` (lesson 07's
`OS_STACK_FILL`), and the loop checks the bottom 16 words every pass — a
**canary**. Experiment 8 recurses until its locals are 32 bytes below
`_stack_floor`, returns *normally*, and the next check fires:

```
*** STACK OVERFLOW: the canary at _stack_floor is damaged - resetting
```

The same paint gives the **high-water mark** `stats` prints, as in lesson 07.

*Why not the MPU?* The C031 has one (`__MPU_PRESENT 1`), and a no-access
region at the floor would turn the overflow into a HardFault. But the core's
own exception entry then pushes eight words onto the **same** overflowing
stack, faults again *inside* HardFault entry, and Armv6-M stops the core:
**lockup**. The canary is the honest tool on this core.

Three questions decide whether one works:

1. **Who feeds it** — and does feeding prove anything? (slides 20–21)
2. **What clocks it** — does it keep counting if the thing it guards stops?
3. **Can the program it guards turn it off?** It must not be able to.

The C031 has two hardware watchdogs. The **IWDG** has its own oscillator,
the LSI (~32 kHz); the **WWDG** counts the bus clock and adds a *window*.
Once started, neither can be stopped except by a reset.

## Slide 17: The IWDG — Four Keys

No enable bit. Everything goes through `KR`, with 16-bit keys a runaway
program is unlikely to write by accident (`stm32c0xx_hal_iwdg.h`):

```c
IWDG->KR  = 0xCCCC;     /* start - and force the LSI on: irreversible */
IWDG->KR  = 0x5555;     /* unlock PR, RLR, WINR                       */
IWDG->PR  = pr;         /* LSI / (4 << pr)                            */
IWDG->RLR = rlr;        /* count rlr .. 0                             */
while (IWDG->SR & (IWDG_SR_PVU | IWDG_SR_RVU | IWDG_SR_WVU)) ;   /* bounded in wdog.c */
IWDG->KR  = 0xAAAA;     /* feed                                       */
```

That order is ST's own `HAL_IWDG_Init()`. The wait is because `PR` and `RLR`
live in the slow LSI clock domain: `SR` says the values have crossed.

```regs
# 1000 ms: PR = 1 (/8), RLR = 3999
IWDG->PR ; LSI / (4 << PR) | 32 = 0x00000001 | !2:0 PR
IWDG->RLR ; counts RLR..0 | 32 = 0x00000F9F | !11:0 RL
IWDG->SR ; update in progress | 32 | 2 WVU, !1 RVU, !0 PVU
```

`timeout = (RLR + 1) × (4 << PR) / LSI` — 125 µs to 32.768 s, exactly the
HAL's "~125us / ~32.7s". **Measured on the host:** `iwdg_pick()` checked for
every whole millisecond from 1 to 32 768 — never early, at most one tick
late, always the finest prescaler that fits.

## Slide 18: The WWDG — a Window, and a Shorter Reach

```regs
# 699 ms, the longest at 48 MHz: WDGTB = 7 (/128), T = 0x7F, window off (W = 0x7F)
WWDG->CR ; WDGA can be set, never cleared | 32 = 0x000000FF | !7 WDGA, !6:0 T
WWDG->CFR | 32 = 0x0000387F | !13:11 WDGTB, 9 EWI, 6:0 W
```

From ST's `stm32c0xx_hal_wwdg.c`: the counter `T` resets the chip when it
rolls from `0x40` to `0x3F`, and

```
WWDG clock = PCLK / (4096 × 2^WDGTB)          timeout = (T[5:0] + 1) / WWDG clock
```

At PCLK = 48 MHz the longest timeout is 64 × 4096 × 128 / 48 MHz =
**699 ms** (**measured on the host**: `699050 µs`). Ask `wdt 1000` with the
WWDG armed and it gets 699.

The *window*: feed **before** the counter falls below `W` and the WWDG resets
you too. It catches code that runs too *fast* — a loop that skipped its work.
`W = 0x7F` switches it off; Lab Part 7 switches it on. `EWI` gives an
interrupt at `0x40`, one tick before the reset: time to log, not to recover.

## Slide 19: Which Dog Will You See Bite? Three Dogs

Wokwi's Nucleo-C031C6 page lists **IWDG: not implemented**, **WWDG:
"Implemented, not tested yet"**, PWR and DBG not implemented, RCC partial. A
watchdog that cannot bite in the simulator teaches nothing, so this firmware
has three:

| Dog | Clock | Armed | In Wokwi | On silicon |
|---|---|---|---|---|
| **soft** | SysTick interrupt | at boot, 1000 ms | **bites** | bites, unless interrupts stop |
| **WWDG** | PCLK / 4096 / 2^WDGTB | `arm wwdg` | untested by Wokwi | bites; ≤ 699 ms |
| **IWDG** | LSI, its own oscillator | `arm iwdg` | **never bites** | bites — the one to ship |

```c
void SysTick_Handler(void)
{
    ms_now++;
    if (wd_mode == WD_ISR) { dog_feed(); }
    if (dog_soft_tick()) {
        crash_rec.uptime_ms = ms_now;
        crash_reset(RW_SOFTDOG);
    }
}
```

The soft dog's weakness is its clock: it **is** an interrupt. Experiment 10
hangs with interrupts off — and the soft dog stops counting with it. Only a
dog with its own clock catches that. In Wokwi that may be the WWDG; on
silicon, the IWDG.

## Slide 22: How Tight Can the Timeout Be?

A heartbeat round lasts as long as the **slowest** job — 250 ms here — plus
anything that blocks the loop. **Measured on the host:**

| | worst feed gap | tightest safe timeout | a hang then caught in |
|---|---|---|---|
| no long prints | 275 ms | **280 ms** | 30 ms |
| with one 180 ms `report` | 455 ms | **460 ms** | 210 ms |

Two lessons in two rows. A single **blocking print** nearly doubles the
safe timeout — printf at 115 200 baud costs 87 µs a character, and it holds
the loop the whole time. And the timeout is a **budget**, set from the
measured worst case plus margin, never from a guess.

On the board, `stats` prints the **worst gap** actually seen since the last
`wdt`. Lab Part 5 is a contest: lowest `wdt` that survives five minutes of
your own use.

## Slide 23: The Post-Mortem of a Watchdog Reset

A hardware watchdog reset runs **no** handler: there is no moment to write a
record. So the loop writes one continuously — its own timestamp and each
job's last check-in, every pass, into `.noinit`:

```c
static void checkin(uint32_t bit, unsigned job)
{
    hb_checkin(&hb, bit);
    crash_rec.job_ms[job] = ms_now;
}
```

After the reset the boot report compares them:

```
---- a WATCHDOG reset us (armed: soft timeout 1000 ms) ----
  running: starve
  main loop's last pass at 14209 ms; last check-ins:  blink -59 ms  input -9 ms  screen -1009 ms
  diagnosis: a JOB stopped while the loop kept running (starved)
```

(The shape of the output, from the format strings — the numbers are
illustrative, not observed.) Every job current but no loop pass means the
loop itself stopped: **hung**. One job far behind: **starved**.

## Slide 24: Power — WFI, and What Sleep Means on the C0

The idle loop does not spin. It executes **`WFI`** — Wait For Interrupt — and
the core stops its clock until the next interrupt.

```regs
# SCB->SCR picks how deep WFI sleeps; PWR->CR1 picks which deep mode
SCB->SCR ; 0 here: plain Sleep | 32 = 0x00000000 | 4 SEVONPEND, !2 SLEEPDEEP, 1 SLEEPONEXIT
PWR->CR1 ; used only when SLEEPDEEP = 1 | 32 | 5 FPD_SLP, 3 FPD_STOP, !2:0 LPMS
```

| Mode | How | Clocks | Exit | SRAM |
|---|---|---|---|---|
| **Sleep** | `WFI`, `SLEEPDEEP = 0` | core stopped, peripherals running | any enabled interrupt | kept |
| **Stop 0** | `LPMS = 000`, `SLEEPDEEP = 1` | all stopped but LSI, LSE | an EXTI line | kept |
| **Standby** | `LPMS = 011` | all stopped but LSI, LSE; regulator off | WKUP pin, RTC, NRST, IWDG, BOR — as a **reset** | **lost** |
| **Shutdown** | `LPMS = 100` | all off but LSE | WKUP pin, RTC, NRST — as a **reset** | **lost** |

The table is ST's own description in `stm32c0xx_hal_pwr.c`; the `LPMS` values
are `LL_PWR_MODE_STOP0`, `_STANDBY`, `_SHUTDOWN` (`stm32c0xx_ll_pwr.h`); the
sequence — set `LPMS`, set `SLEEPDEEP`, `WFI` — is `HAL_PWR_EnterSTOPMode()`.
Note the last two: waking from Standby or Shutdown *is* a reset, so `.noinit`
does not survive them. This lesson uses **Sleep only**: Wokwi does not
model PWR at all, and a simulator has no current to measure. `WFI` is a core
instruction, so it runs in any simulator — what it *saves* cannot be seen
there.

## Slide 25: Measuring CPU Load With the Clock You Already Have

The M0+ has no cycle counter. SysTick is one: it counts 47 999 → 0 every
millisecond. Read it either side of the sleep:

```c
__disable_irq();
if (ms_now == t) {
    uint32_t v0 = SysTick->VAL;
    __WFI();                                    /* sleep: SLEEPDEEP = 0 */
    uint32_t v1 = SysTick->VAL;
    idle_cycles += systick_elapsed(v0, v1, SysTick->LOAD);
}
__enable_irq();                                 /* handlers run here */
```

- **Interrupts off around `WFI`** — `WFI` still wakes on a pending interrupt
  with PRIMASK set (Armv6-M), but the handler waits until `__enable_irq()`.
  So `v1` is read *before* any handler: the measurement is pure sleep, and no
  tick can sneak in between the test and the `WFI`.
- `systick_elapsed()` handles the reload wrap (**measured on the host**: 4
  cases including the wrap).
- `load = 1000 − idle_ms × 1000 / window`, per mille, every second.

`sleep off` spins on the same condition instead: same load figure, but the
core never sleeps. *That* difference is current, and only silicon shows it.

## Slide 26: HAL vs CMSIS — the Same Store

ST's HAL for the C0 (`stm32c0xx_hal_gpio.c`, STM32CubeC0, © 2022
STMicroelectronics), verbatim:

```c
void HAL_GPIO_WritePin(GPIO_TypeDef *GPIOx, uint16_t GPIO_Pin, GPIO_PinState PinState)
{
  /* Check the parameters */
  assert_param(IS_GPIO_PIN(GPIO_Pin));
  assert_param(IS_GPIO_PIN_ACTION(PinState));

  if (PinState != GPIO_PIN_RESET)
  {
    GPIOx->BSRR = (uint32_t)GPIO_Pin;
  }
  else
  {
    GPIOx->BRR = (uint32_t)GPIO_Pin;
  }
}
```

Compiled with this course's flags (`assert_param` empty, as in a release
build) next to the CMSIS line, `GPIOA->BSRR = 1u << 5;`:

| | instructions on the path | the store |
|---|---|---|
| `HAL_GPIO_WritePin(GPIOA, 1 << 5, GPIO_PIN_SET)` | 11 (args, `push`, `bl`, `cmp`, `beq`, `str`, `bx`, `pop`) | `str r1, [r0, #24]` |
| `GPIOA->BSRR = 1u << 5` | 4 | `str r2, [r3, #24]` |

The store is **the same instruction**. The HAL adds a call and a test —
cheap. Its real costs are elsewhere: `HAL_IWDG_Init()` times out using
`HAL_GetTick()`, which needs SysTick running *HAL's* way, and handles,
callbacks and `HAL_Init()` come with it. Use HAL to **read** what ST does
(this lesson took the IWDG and WWDG sequences from it); write registers when
you need to know exactly what happens.

## Slide 29: What Carries Forward

- **Every application lesson ships the flight recorder.** A drone that
  resets mid-flight (13–14), a robot that stops in a race (15–18): the first
  question is always *why did it reset?* — `.noinit` and `CSR2` answer it.
- **The heartbeat is how a failsafe is fed.** Lesson 14's failsafe and
  lesson 18's tournament robot both need "every task alive", not "the timer
  still ticks".
- **Timeouts are budgets.** The 460 ms here, lesson 09's 2000 polls, the
  control loop's deadline in Part 3: measure the worst case, add margin,
  write it down.
- **When pc is nonsense, read lr.** It will save you an afternoon.
