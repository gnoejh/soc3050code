## What this lab is

**A guided walkthrough, not a test.** A parking sensor: an HC-SR04 ranger
timed by input capture, a servo gauge driven by PWM, a proximity bar on the
LEDs, all scheduled from an interrupt-driven millisecond. You will measure the
timers against each other, break each one in a way that builds with zero
warnings, and finally find out something the simulator's documentation does
not say.

Each part says **Do this**, asks you to **guess**, then explains. **Put every
change back before the next part** unless told otherwise.

## Part 0 — Build it, run it (20 min)

```
build.bat
simulate.bat
```

Zero warnings:

```
           FLASH:        7340 B        32 KB     22.40%
             RAM:        2040 B        12 KB     16.60%
```

Paste `diagram.json` into the Wokwi tab (a servo, an HC-SR04 and the LED bar),
upload `Main.elf`.

### Read the banner

```
-- SysTick --
  LOAD = 47999  ->  1000 interrupts/s    handler installed
-- TIM3: PWM on PA6 (AF1) --
  PSC = 47  ARR = 19999  ->  50 Hz update, 1 count = 1 us
  CCR1 = 1500 us pulse    TIM3_IRQHandler installed
-- TIM14: input capture on PA7 (AF4) --
  PSC = 47  ARR = 65535  ->  1 count = 1 us, wraps every 65.5 ms
  CCER CC1P/CC1NP = 1/1 (both edges)    TIM14_IRQHandler installed
```

Every number was read back from a register. **Check one by hand**: 48 MHz ÷
(47 + 1) ÷ (19999 + 1) = ?

> 50 Hz. Both registers hold *N − 1* (slide 5b), which is why the arithmetic
> needs the `+ 1`s.

### Read the report

One line a second:

```
t=  3000 ms  TIM3 50/s  echo  5800 us = 100 cm  servo 1500 us  (last line took 8 ms)
```

Now **click the HC-SR04** in the diagram. A slider appears. Drag it.

**Guess first:** at 20 cm, how many LEDs, and which way does the servo swing?

> 20 cm is 10% of the 200 cm full scale, so 90% proximity: `(200 − 20) × 8 /
> 200 = 7` LEDs, and the servo target is `2000 − 20 × 1000 / 200 = 1900 µs`.
> The report's `servo` column **glides** there at 20 µs per 20 ms frame —
> about 0.4 s for a 400 µs move — because the TIM3 interrupt rate-limits it
> (slide 11).

**Two things to notice in the report line:**

> - `TIM3 50/s` — TIM3's update interrupts counted against SysTick's clock.
>   Two dividers, one crystal, and they agree. That is a self-test (slide 16).
> - `took 8 ms` (or 7) — the previous `printf` blocked the loop for that long,
>   and `t=` still advances by exactly 1000 each line. In lesson 05 those
>   milliseconds would have been lost. If yours says 0, Wokwi's UART is faster
>   than silicon's 86.8 µs per character — note it.

## Part 1 — Clear the flag the EXTI way (15 min)

In `TIM3_IRQHandler()`, change the clear to what worked in lesson 05:

```c
        TIM3->SR = TIM_SR_UIF;          /* was ~TIM_SR_UIF */
```

Rebuild — zero warnings — and re-upload.

**Guess first:** does anything run at all?

> **The banner stops part-way through**, and nothing after it ever appears.
> (Printing the banner takes about 60 ms at 115200 baud, so the freeze lands
> mid-banner. If Wokwi's UART is faster than silicon's, the banner may finish
> and the report lines simply never start — same cause.)
>
> Writing `1` to a timer flag does nothing — timer flags clear on **0**
> (slide 7). So `UIF` stays set, and 20 ms after `servo_init()` the handler
> starts tail-chaining into itself forever. The banner was still printing at
> the time; it stops wherever it had got to. `SysTick_Handler` (priority 3)
> can never get in past TIM3 (priority 2), so time stops too.
>
> **And the servo still holds its position.** PWM is generated by the timer
> hardware; it needed the CPU only to *change* `CCR1`. The CPU is lost in a
> loop and the waveform does not care.
>
> Meanwhile the line you wrote did clear something: every **other** flag in
> `SR`. That is why ST writes `~flag` — ones leave flags alone, so the
> complement clears exactly one.

## Part 2 — The off-by-one (10 min)

In `servo_init()`, drop the `− 1u` from the prescaler:

```c
    TIM3->PSC  = SystemCoreClock / TICK_HZ;         /* 48 instead of 47 */
```

Rebuild, re-upload, watch the report.

**Guess first:** what does `TIM3 ../s` read now?

> 48 000 000 ÷ 49 ÷ 20 000 = **48.98 Hz**. Measured in Renode: `48/s` in the
> first second, then `49/s` every second after.
>
> The banner still says `PSC = 48 ... 48 Hz update` (integer division), and
> every servo pulse is now 2% long — `CCR1 = 1500` gives 1531 µs. Nothing
> else complains. **Only the cross-check caught it**, and only because it
> compares two clocks that should agree exactly. That is what a self-test is
> for.

## Part 3 — Slew (10 min)

`SERVO_SLEW_US` is the most the pulse may move per frame. Try `1000`, then
`2`.

> At 1000 the limiter never limits: the servo **snaps** to each new reading,
> and any noise in the echo jitters it. At 2 it takes 500 frames — **10
> seconds** — to cross the full 1000 µs range: smooth, and useless as a gauge.
>
> This is the first tuning trade-off of the course: **responsiveness against
> smoothness**. Every controller in Part 3 has the same dial, with better
> maths behind it.

## Part 4 — Measure what the documentation does not say (20 min)

Wokwi's servo page describes 0–180° with hard stops, and gives **no pulse
widths**. Find them.

In `main()`, replace the gauge mapping so the slider drives the pulse
directly:

```c
            servo_target_us = 400u + cm * 10u;     /* was gauge_us(cm) */
```

Rebuild, re-upload. The slider now sets the pulse directly — 400 µs at 0 cm,
2600 µs at 220 cm (stay below that; nothing clamps it now) — and the report
prints it. Move slowly from each end and write
down **the pulse at which the horn stops moving**.

> There is no answer printed here, deliberately: nobody has measured it yet,
> and the course would rather you did than quote a number from a forum.
> Useful references to compare against: the nominal 1000–2000 µs of slide 9,
> and Arduino's `Servo` library default of 544–2400 µs.
>
> Then set `SERVO_MIN_US` and `SERVO_MAX_US` to what you measured, restore
> `gauge_us(cm)`, and your gauge uses the servo's full travel.

## Part 5 — The wrong alternate function (10 min)

At the top of `Main.c`:

```c
#define AF_TIM3         2u          /* was 1u */
```

**Guess first:** what does the report say?

> `TIM3 50/s`. **The timer works perfectly** — it counts, it updates, it
> interrupts, the slew logic runs, `CCR1` moves. And the servo does not.
>
> The banner shows `PWM on PA6 (AF2)`. On PA6, AF2 is not TIM3; the pin is
> connected to a different peripheral's output, or to none. This is the pure
> form of the silent failure: every register you can read looks right except
> the one that connects the inside of the chip to the outside.

## Part 6 — Which path measured it, and lose one edge (15 min)

### Step 1. Read the source

Run the unchanged program and read the end of a report line:

```
echo  5882 us = 101 cm (EXTI)  servo 1495 us  edges cap 0 exti 141
```

**Guess first:** the lesson is about input capture. Why does the line say
`(EXTI)`, and why is `cap` 0?

> **Wokwi does not implement timer input capture.** This is what it printed
> when this lesson was first watched, on 2026-10-04: `cap` stayed at 0 for
> the whole run while `exti` climbed by 20 a second, two edges for each of
> the 10 pings. Wokwi's board page lists the STM32 timers as "used by
> analogWrite()": PWM out, nothing in. PA7 also feeds EXTI line 7, whose
> handler stamps each edge from `TIM14->CNT` (slide 13b), so the measurement
> still works. It is just late by the interrupt latency, which is exactly what
> input capture exists to remove (slide 12). On a real Nucleo, `cap` counts
> too and the source reads `(capture)`.
>
> 5882 us for the slider's 100 cm is 58.8 us per cm. That is the speed of
> sound, 340 m/s, there and back; the program's `/ 58` rounds it to 101 cm.

### Step 2. Lose one edge

In `echo_exti_init()`, delete the falling-edge line:

```c
    EXTI->FTSR1 |= 1u << line;                       /* falling: echo ends      */
```

**Guess first:** what does `exti` count now, and what does the echo read?

> `exti` climbs half as fast, 10 a second, and the line reads
> `echo 0 us = 0 cm (none)` for ever. The bar stays dark and the servo stays
> at 1500 us: they change only when a measurement completes, and none does.
>
> Every edge is now a rising edge. The handler stores `exti_rise` each time;
> the falling branch never runs, so no width is ever finished. Measuring a
> pulse needs both edges. Input capture has the same rule: on a real board,
> capturing on `CC1E` alone, without `CC1P | CC1NP`, fails the same way. Two
> channels, one per edge, is what ST calls *PWM input mode*.

Put the line back.

## Part 7 — A parking beeper (open-ended)

A real parking sensor beeps faster as you get closer. Make **LD4** do that:
blink with a period that shrinks with distance, and stay **solid** below
10 cm.

Rules: no `delay`, no busy-waiting, nothing that stops the ranger, the
report or the servo. Only `millis()` and the `now - then` pattern of slide 4.

> One working version replaces the heartbeat block: a period of `cm × 5`
> milliseconds, and `LD4` forced on when `cm < 10`. It builds to 6796 B FLASH,
> 8 bytes more than the original, with zero warnings.
>
> Notice what you did *not* have to touch: the other three jobs. That is the
> property the non-blocking loop buys you — and the property a single slow
> job would destroy, which is lesson 07's starting point.
