Fixed Point and DMA: Maths Without an FPU, Data Without the CPU

SOC3050 ARM Edition — Part 2, Systems

Reference: STM32 Reference Manual ·
Board manual: UM2953, STM32 Nucleo-64 boards (MB1717)

How fast is maths on a chip with no FPU? Race the number formats and find
out.

The Cortex-M0+ has no floating-point unit. Every float multiply is a
function call. So this lesson builds an arena: the same seven jobs — add,
multiply, divide, sine, rotate a point, a PI controller step, a 16-tap filter
— written in int32, Q15, Q16.16 and float, timed with SysTick, and
ranked. Then the second half takes work off the CPU altogether: the DMA
fills RAM with joystick readings while the processor does nothing at all.

Figures marked measured on the host come from two programs in host/:
test_fix (accuracy, against double precision) and m0sim.py, a Cortex-M0+
instruction model that executes this lesson's own Main.elf and counts cycles
(slide 15). Nothing here has been watched running in Wokwi — and the DMA
half cannot be: Wokwi's C031C6 does not implement DMA (slide 24).

The Board: This Lesson's Pins

Before any register, find the pins. Every highlighted dot is a header pin that
this lesson's diagram.json wires something to — the same circuit you paste
into Wokwi — at its position on the Nucleo-C031C6, to scale. A label reads
MCU pin (header name, if different) and what the pin does here.

The two outer double rows are ST's morpho headers, which reach every pin
of the chip; the two inner single rows are the Arduino-compatible header
(A0–A5 on the left, D0–D15 on the right). Some MCU pins appear on both — PA5 is
also D13 — so the highlighted position is the one this lesson's wire uses.
The real board's headers are drawn in its manual, UM2953 (top bar).

The Chip: The Same Pins, as Port Bits

Inside the chip the header positions disappear: every pin is one bit
position in its port's registers. Pin n of GPIOA is bit n of
GPIOA->IDR, bits 2*n*+1 : 2*n* of GPIOA->MODER, and so on (lesson 05,
slide 4). Each cell below is one pin, drawn in register order, marked with how
this lesson configures it.

This was compiled and disassembled, not run: no M4F is in this course. It

answers it.

Slide 3: What __aeabi_fmul Has to Do

A float is three fields packed in 32 bits. Multiplying two of them in
software means:

  1. unpack: split sign, exponent, mantissa; put back the hidden leading 1
  2. handle zero, infinity, NaN, denormals — every call checks
  3. multiply two 24-bit mantissas — a 48-bit product, on a CPU whose MULS keeps 32
  4. add the exponents, renormalise, round to nearest even
  5. check for overflow and underflow, pack

The M0+ does it in 162 cycles per iteration of the multiply loop, against
15 for an integer multiply (measured on the host, slide 16). And it costs
flash: the soft-float routines this lesson links add up to 4292 bytes —
13% of the chip — measured with nm (slide 17).

Slide 4: Fixed Point — an Integer With an Agreed Binary Point

The step is fixed: 1.5 × 10⁻⁵ whether the number is 0.001 or 30 000. A
float's step scales with the number. That is the whole trade: fixed point
gives up range to keep integer speed.

fix.h builds constants at compile time — Q16(0.8) is 52429, folded by the
compiler, so no float code reaches the chip.

Slide 5: The Arithmetic Rules

add     Qn + Qn  = Qn           plain integer add          (same binary point)
mul     Qn x Qn  = Q2n          shift right by n afterwards
          Q15    x Q15    = Q30     -> 32 bits: ONE MULS
          Q16.16 x Q16.16 = Q32.32  -> 64 bits: __aeabi_lmul

From fix.h:

static inline q15_t q15_mul(q15_t a, q15_t b)
{
    int32_t p = (int32_t)a * b;      /* Q30, fits in 32 bits          */
    p += 1 << 14;                    /* + half an LSB: round           */
    return q15_sat32(p >> 15);       /* back to Q15, clamp -1 x -1     */
}

static inline q16_t q16_mul(q16_t a, q16_t b)
{
    int64_t p = (int64_t)a * b;      /* Q32.32: needs 64 bits          */
    p += 1 << 15;
    return q16_sat64(p >> 16);
}

Same three lines. One of them is ten times cheaper than the other, and the
difference is entirely whether the product fits in a register.

Slide 6: Q15 Multiply, on the Chip

q15_mul as the compiler emitted it in this lesson's Main.elf:

08000ecc <q15_mul>:
  movs  r3, #128
  muls  r0, r1            <- the multiply: 1 instruction
  lsls  r3, r3, #7        r3 = 0x4000, half an LSB
  adds  r0, r0, r3        round
  movs  r3, #128
  asrs  r0, r0, #15       back to Q15
  lsls  r3, r3, #8        r3 = 0x8000
  cmp   r0, r3            only ONE overflow test ...
  blt.n 8000ee0
  ldr   r0, [pc, #4]      ... clamp to 0x7FFF
  sxth  r0, r0
  bx    lr

Look at what is missing: a test for the bottom of the range. The compiler
proved that a Q15 × Q15 product can never be below −1, so it dropped the
< -32768 branch from q15_sat32. Only −1 × −1 = +1 can overflow, and only
upwards.

Measured on the host: 34 cycles per iteration for the Q15 multiply loop,
against 15 for int32 and 162 for float.

Slide 7: Q16.16 Multiply Needs 64 Bits

The M0+'s MULS returns the low 32 bits of a product. Q16.16 needs the
middle 32 of a 64-bit product, so gcc calls __aeabi_lmul — four 16 × 16
multiplies stitched together:

080031c0 <__aeabi_lmul>:
  ...
  muls  r0, r5            lo x lo
  muls  r1, r6            lo x hi
  muls  r5, r3            hi x lo
  muls  r6, r3            hi x hi
  adds  r5, r5, r1        add the cross terms ...
  ...                     ... and propagate the carries
  muls  r2, r7            the high words' contribution
  muls  r4, r3
  ...
  pop   {r4, r5, r6, r7, pc}

78 bytes of flash, and the whole Q16.16 multiply loop costs 104 cycles per
iteration (measured on the host): faster than float's 162, but three
times Q15's 34.

The rule this gives you: choose the narrowest Q format that holds your
numbers. Q15 for anything normalised to ±1 — samples, sines, gains;
Q16.16 only when you need the range.

Slide 8: Rounding — Truncation Drifts

Shifting right truncates toward −∞. Every product comes out low by up to
one LSB, half an LSB on average. Adding half an LSB before the shift rounds to
nearest instead.

Measured on the host, one million random Q15 products:

mean error
round to nearest (q15_mul)−0.0000 LSB
truncate (>> 15 alone)−0.4992 LSB

A bias of −0.5 LSB looks harmless. Now put it inside a filter or an
integrator that runs a thousand times a second: the error does not average
out, it accumulates in one direction. An integrator built on truncating
multiplies drifts even with zero input.

Cost of rounding: one adds (slide 6). Always pay it.

Slide 9: Overflow — Saturate, Don't Wrap

Integer overflow on this CPU wraps round: the largest positive number plus one
is the most negative. Measured on the host (test_fix, part 3):

casewrappingsaturating (fix.h)
Q15 0.75 + 0.5−0.75000+0.99997
Q15 −1 × −1−1 (32768 does not fit in int16_t)+0.99997
Q16.16 300 × 300garbage+32767.99998 (the top of the range)
Q16.16 1 / 0(a division by zero)+32767.99998

A wrapped value is not slightly wrong — it has the wrong sign. In a motor
controller, "full forward" becomes "full reverse". Saturation is still wrong,
but wrong in the safe direction.

fix.h keeps a deliberately broken q15_add_wrap() so Lab Part 4 can watch
the sign flip.

Slide 10: Guard Bits — Why the FIR's Accumulator Is Safe

The 16-tap filter adds 16 Q30 products into one int32_t:

int32_t acc = 0;
for (j = 0; j < 16; j++) acc += (int32_t)fir_h_q15[j] * x[k + j];
return q15_sat32((acc + (1 << 14)) >> 15);      /* round once, at the end */

Each product is up to 2³⁰. Sixteen of them could reach 2³⁴ — but the
coefficients are all positive and sum to 1, so the sum never exceeds the
largest input. That is a design property, not luck.

Measured on the host: scale the same coefficients to a gain of 4 and feed
a full-scale input:

FIR  gain 4, full-scale input: 32-bit sum -0.0004, 64-bit sum +3.9996

The 32-bit accumulator wrapped round to nearly zero. A filter that "goes
quiet" on its loudest input is the classic fixed-point bug. The cures: keep
the gain ≤ 1, scale inputs down (spend guard bits), or accumulate in 64 bits
and pay for it.

Slide 11: Division — No Instruction at All

The Cortex-M0+ has no divide instruction. ARMv6-M simply does not define
one. Every / is a call:

routineflashcycles / iteration (host model)
int32 / int32__aeabi_idiv470 B62
float / float__aeabi_fdiv(in the 4292 B)457
Q16.16 (a << 16) / b__aeabi_ldivmod (64-bit)604 B663

Q16.16 division loses to float: it needs a 64-by-64-bit divide, and libgcc's
is general-purpose.

The cure is old: divide by a constant? Multiply by its reciprocal.
x / 10 becomes q16_mul(x, Q16(0.1)) — 104 cycles instead of 663. The
compiler does this itself for integer constants; for fixed point, you do.

Slide 12: Sine, Three Ways

The table takes a binary angle: a full turn is 65 536, so the angle wraps
for free when the uint16_t overflows — no range reduction at all.

uint32_t quadrant = angle >> 14;          /* bits 15:14 pick the quadrant   */
uint32_t i = a >> 8, frac = a & 0xFF;     /* bits 13:8 the entry, 7:0 between */
int32_t  y = y0 + (((y1 - y0) * frac + 128) >> 8);

1.1 × 10⁻⁴ is 0.006° of angle error — finer than any hobby IMU can measure.
51× faster than sinf, and 24× less flash.

Slide 13: Measuring Cycles — SysTick as a Stopwatch

This lesson does not link the RTOS, so it owns SysTick — not as a 1 ms tick,
but as a free-running 24-bit cycle counter:

One count per CPU cycle, 20.8 ns. It counts down, and wraps every
2²⁴ cycles = 349 ms:

static inline uint32_t cycles_since(uint32_t t0)
{
    return (t0 - SysTick->VAL) & SysTick_LOAD_RELOAD_Msk;    /* 0xFFFFFF */
}

Then, for each workload: time fn(64), time fn(0), subtract, divide by 64.
The subtraction cancels the call, the return and reading SysTick itself.
Best of three runs.

cycles_init() also checks that VAL moves before trusting it — lesson 09
met a simulator where SysTick was enabled and frozen.

Slide 14: The Overhead You Must Subtract

Row 0 of the arena is a loop that does almost nothing:

for (i = 0; i < n; i++) { acc += (uint32_t)in_ia[i & 63]; }

12 cycles per iteration in the host model: compare, branch, mask, shift,
load, add, increment. Every other row includes those 12. An int32 add row
measures 15 — so the add itself, plus a second load, is 3 cycles.

The firmware prints both: cyc/iter (raw) and net (minus the baseline).

This is the measurement lesson in miniature: measure the empty
experiment. A benchmark that does not know its own overhead reports the
loop, not the operation — and for int32 the loop is 80% of the number.

Slide 15: A Second Witness — the M0+ Model

Nothing can be run in Wokwi from here, so the cycle counts needed another
source. host/m0sim.py (Python standard library, about 500 lines):

  • loads this lesson's Main.elf — the same machine code, libgcc soft float and newlib sinf the board runs;
  • executes ARMv6-M Thumb instruction by instruction;
  • counts cycles from the Cortex-M0+ TRM's timing table — ALU 1, load/store 2, taken branch 2, BL 3, PUSH/POP 1 + N;
  • calls bench_seed(2026) then every workload, exactly as Main.c does.

And it checks itself: each workload returns a checksum of all its results.
For 21 of 22 workloads, the model's checksum is bit-identical to the
PC's (test_fix, compiled by host gcc from the same C). IEEE 754 requires
+ − × ÷ to round identically everywhere, so this is a strong test that both
the simulator and libgcc did exactly the right arithmetic. The 22nd is sinf:
newlib's and MinGW's are different code.

Two assumptions, both printed: a single-cycle multiplier (an M0+ build
option; --mul 32 tries the other) and zero wait states (a second column
adds a crude 1-wait-state model).

Slide 18: When Float Is Fine

Float is ten times slower. That matters only if you are short of cycles.
The budget arithmetic, with the host model's numbers, at 48 MHz:

PI step, float   784 cycles x  500 Hz =   392 000 cycles/s =  0.82 % of the CPU
FIR16,   float  4271 cycles x 1000 Hz = 4 271 000 cycles/s =  8.9 %  of the CPU
FIR16,   Q15     302 cycles x 1000 Hz =   302 000 cycles/s =  0.63 % of the CPU

A control loop at a few hundred hertz — lessons 13–18's drone and robots —
spends under 1% of the CPU on a float PI step. Even a hundred float
operations per loop at 250 Hz is about 4 M cycles/s, under 10%. Write it in
float, with fmath.h instead of libm. That is what the application
lessons do.

Reach for fixed point when the rate is high (audio, a 10 kHz motor current
loop, filtering every ADC sample), when the budget is tight, or when the flash
is: Q15 does the FIR at 1 kHz for 0.63% and no soft-float library at all.

The decision is arithmetic, not taste. Do the multiplication before you
choose.

Slide 20: DMA — a Second Bus Master

The DMA controller is a second bus master: it can read and write memory
and peripherals by itself. The ADC finishes a conversion and raises a
request; the DMAMUX routes it to a channel; the channel copies ADC1->DR
to the next slot of scan_buf and steps its pointer. The CPU is not
involved — not even an interrupt.

The C031 has one DMA controller with three channels, and a DMAMUX in
front of it.

Slide 21: The DMAMUX — Which Request, Which Channel

Two facts the CMSIS header does not contain, both from ST's C0 LL driver:

factsource
ADC1's request is ID 5LL_DMAMUX_REQ_ADC1 = 0x00000005U, stm32c0xx_ll_dmamux.h
memory-to-memory is ID 0LL_DMAMUX_REQ_MEM2MEM = 0x00000000U
DMAMUX channel n feeds DMA1 channel n+1"DMAMUX channel 0 to 6 are mapped to DMA1 channel 1 to 7", stm32c0xx_ll_dma.h

So the ADC's request goes in DMAMUX1_Channel0 to reach DMA1_Channel1:

The synchronisation and event fields stay 0: no triggers, every request
passes straight through. The off-by-one between "channel 0" and "channel 1"
is the kind of thing that is wrong silently — and why both numbers are
cited, not remembered.

Slide 22: One DMA Channel, Four Registers

DMA1_Channel1->CPAR  = (uint32_t)&ADC1->DR;     /* from: the ADC result  */
DMA1_Channel1->CMAR  = (uint32_t)scan_buf;      /* to:   our array       */
DMA1_Channel1->CNDTR = 3;                       /* how many, then wrap   */
DMA1_Channel1->CCR   = DMA_CCR_PSIZE_0 | DMA_CCR_MSIZE_0 | DMA_CCR_MINC
                     | DMA_CCR_CIRC | DMA_CCR_PL_1 | DMA_CCR_EN;
  • PSIZE = MSIZE = 01: 16-bit reads from DR, 16-bit writes to RAM.
  • MINC but not PINC: the RAM address steps by 2; DR stays put.
  • CIRC: when CNDTR reaches 0, reload it and CMAR — forever.
  • DIR = 0: peripheral → memory.

CNDTR counts down: it reads 3, 2, 1 — the number of slots left in this
round. Watching it move is the cheapest proof the DMA is alive (slide 24).

Slide 23: The ADC Side — Scan, Continuous, DMA

  • CHSELRMOD = 0: CHSELR is a bitmask; SCANDIR = 0 converts from the lowest channel up. So scan_buf[0] = PA0 (X), [1] = PA1 (Y), [2] = PA4 (knob). The order is the hardware's, not yours.
  • CONT: start the next scan without being asked.
  • DMAEN: raise a DMA request at every end of conversion; DMACFG = 1 (circular): keep raising them after the DMA's count runs out.

The timing, from the settings: ADC clock 24 MHz (PCLK/2); sampling 160.5
cycles + 12.5 cycles processing at 12 bits (ST's HAL adc.h) = 173 cycles
= 7.21 µs per conversion, 21.6 µs per scan of three — about
46 000 complete scans a second, written into RAM with the CPU idle.

Polled, the same three readings cost the CPU at least 3 × 7.21 µs =
~1040 cycles of waiting each time. Via DMA, reading them is three
loads from RAM. The firmware times both (Lab Part 6).

Slide 24: Trust, But Watch — the Stuck-DMA Detector

Wokwi's page for this board lists what it simulates. DMA is listed as not
implemented (also IWDG, PWR, RTC, SYSCFG, DBG). So in Wokwi the DMA cannot
run, and everything on slides 20–23 is predicted from RM0490 and ST's
drivers — it cannot be observed in the simulator.

The firmware is written for exactly this. It never assumes the DMA ran:

for (i = 0; i < SCAN_CH; i++) scan_buf[i] = 0xFFFF;   /* a 12-bit ADC never writes this */
... start the ADC and the DMA ...
for (i = 0; i < SPIN_LIMIT; i++)
    if (scan_buf[0] != 0xFFFF && scan_buf[1] != 0xFFFF && scan_buf[2] != 0xFFFF)
        return 0;                                      /* proof: all three written      */
scan_stop();                                           /* never moved: undo, and say so */
return -1;

In Wokwi, expect:

  scan: DMA NEVER MOVED - buffer still 0xFFFF after the time limit.
        EXPECTED IN WOKWI: its C031C6 model does not implement DMA (docs.wokwi.com).
        On a real Nucleo this line says RUNNING.  Falling back to POLLED adc_read().

…and everything after it keeps working on polled reads. If the simulator
instead faults on the first DMA register access, a HardFault_Handler
prints !! HardFault during: the DMA demo — and USE_DMA 0 skips it.

This is the lesson's most transferable idea: a peripheral you cannot see
working must prove it is working, at run time, with a value it could not
produce by accident.

Slide 25: Memory to Memory — and a Surprise in memcpy

DMA needs no peripheral at all: MEM2MEM = 1 makes a channel copy as fast as
the bus allows.

What it races: this build's memcpy, from newlib-nano —

08004a32 <memcpy>:
  ...
  ldrb  r4, [r1, r3]     one BYTE at a time
  strb  r4, [r0, r3]
  adds  r3, #1
  b.n   8004a36

newlib-nano is built for size, so its memcpy is a byte loop. Measured
on the host model: a 1 KB RAM-to-RAM copy takes 10 251 cycles — about
10 cycles a byte. The DMA moves 32-bit words, and while it copies, the CPU is
free; the firmware counts how often it polled meanwhile.

In Wokwi dma_copy() will report NEVER COMPLETED and the data WRONG —
the same missing DMA. On a Nucleo, the comparison is Lab Part 7.

Slide 27: What Carries Forward

  • Write the application lessons in float — after doing the arithmetic. Lessons 13–18 run control loops at a few hundred hertz; slide 18 shows that costs about 1% of the CPU per controller. Use fmath.h, never libm's sinf: 4.7 KB and twice the cycles.
  • Fixed point is for rates and budgets. Filtering every ADC sample, audio, a fast motor current loop: Q15, rounded, saturated, with the accumulator's guard bits designed in.
  • Time things. SysTick-as-stopwatch, minus the empty loop, best of three: any later claim that something is "fast enough" should come with a number measured this way.
  • DMA moves data; the CPU decides. On real silicon, lesson 09's I²C reads and lesson 12's OLED frames are DMA's next jobs. In Wokwi they stay polled — and now you know how a program finds that out by itself.
