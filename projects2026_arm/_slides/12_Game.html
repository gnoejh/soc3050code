Game: An Arcade on a 128×64 Screen

SOC3050 ARM Edition — Part 3, Applications

Reference: STM32 Reference Manual ·
Board manual: UM2953, STM32 Nucleo-64 boards (MB1717)

Three games, one joystick, 1 024 bytes of picture — and a bus that cannot
send all of them in time.

Part 3 starts here. Everything from Part 1 comes back at once: GPIO buttons
and their edges (05), a timer making sound (06), SysTick as a clock (06),
frames with checksums (08), the ADC and I²C (09). This lesson adds the two
models every interactive system is built on — a display you update by
difference and a loop that keeps time — and ends in something you will
want to show people: an arcade with SNAKE, BREAKOUT and FLAP.

Figures marked measured on the host come from host/test_games.c, which
compiles the real game files and the real display driver with plain gcc and
plays them with scripted joysticks. Nothing in this deck was watched in Wokwi;
the last two slides say what that leaves open.

The Board: This Lesson's Pins

Before any register, find the pins. Every highlighted dot is a header pin that
this lesson's diagram.json wires something to — the same circuit you paste
into Wokwi — at its position on the Nucleo-C031C6, to scale. A label reads
MCU pin (header name, if different) and what the pin does here.

The two outer double rows are ST's morpho headers, which reach every pin
of the chip; the two inner single rows are the Arduino-compatible header
(A0–A5 on the left, D0–D15 on the right). Some MCU pins appear on both — PA5 is
also D13 — so the highlighted position is the one this lesson's wire uses.
The real board's headers are drawn in its manual, UM2953 (top bar).

The Chip: The Same Pins, as Port Bits

Inside the chip the header positions disappear: every pin is one bit
position in its port's registers. Pin n of GPIOA is bit n of
GPIOA->IDR, bits 2*n*+1 : 2*n* of GPIOA->MODER, and so on (lesson 05,
slide 4). Each cell below is one pin, drawn in register order, marked with how
this lesson configures it.

Slide 2: Two Halves — Platform and Game

The games never read a clock, a pin or a register. They get a pad_t once per
tick, draw into RAM, and ask for sounds through one hook, sfx(). Main.c is
the only file that includes stm32c031xx.h. On a PC, host/test_games.c
supplies sfx(), on_score() and a counting i2c_write_read(), and the same
three games run there unchanged.

This split is the lesson's most reusable idea. Part 3's low-level contract,
control_step(sensors_t *, actuators_t *), is the same shape for a drone and a
robot: the "game" becomes a controller, and the PC a physics simulator.

Slide 3: The SSD1306 — 1 KB of Picture at the End of Two Wires

The panel is a 128 × 64 OLED with its own controller, the SSD1306, at I²C
address 0x3C (Wokwi's board-ssd1306 default; some modules use 0x3D). The
controller holds the picture in its own RAM and refreshes the glass by itself;
the MCU only writes into that RAM.

Not rows of pixels, as on a PC — vertical strips of eight. That one fact
shapes everything below: the unit of transfer is a byte that is a column, and
the natural unit of "this part changed" is a page, 8 rows deep.

Slide 4: A Pixel Is a Bit — Which Byte, Which Bit

Pixel (x, y) is bit (y % 8) of byte fb[y / 8][x]. In oled.c:

void oled_pixel(int x, int y, int colour)
{
    if ((unsigned)x >= OLED_W || (unsigned)y >= OLED_H) { return; }
    uint8_t *b = &fb[y >> 3][1 + x];
    uint8_t  m = (uint8_t)(1u << (y & 7));
    uint8_t  old = *b;
    if (colour == OLED_ON)       { *b |= m; }
    else if (colour == OLED_XOR) { *b ^= m; }
    else                         { *b &= (uint8_t)~m; }
    if (*b != old) { dirty |= (uint8_t)(1u << (y >> 3)); }
}

The byte at fb[1][40] — column 40, rows 8 to 15 — with pixels (40, 9) and
(40, 12) lit:

Three details worth stealing:

  • (unsigned)x >= OLED_W clips both ends in one compare: a negative x becomes a huge unsigned number. Off-screen is never an error, so a sprite can slide off the edge.
  • y >> 3 and y & 7 are / 8 and % 8 without the division the M0+ does not have.
  • The last line: a page becomes dirty only if a byte really changed. Drawing a pixel that is already lit costs a few cycles and no bus at all.

Slide 5: Every Write Starts With a Control Byte

Over I²C the SSD1306 receives one stream of bytes. The byte after the address
says what the rest are:

D/C# is data (1) or command (0); Co = 0 means "no more control bytes, the
rest is all one kind". oled.c sends exactly two kinds of transfer:

S | 0x3C+W | A | 0x00 | A | cmd | A | cmd ... | P        commands
S | 0x3C+W | A | 0x40 | A | px  | A | px  ... | P        128 pixel bytes

And one trick that costs nothing: each page in RAM is 129 bytes, the first
permanently 0x40. So a page goes out as one i2c_write_read(0x3C, fb[p], 129,
0, 0) straight from the framebuffer — no copying into a transmit buffer:

static uint8_t fb[OLED_PAGES][1 + OLED_W];  /* [0] = 0x40, then 128 */

perfectly, and the glass stays black because nothing generates its drive
voltage. It is lesson 09's MPU6050 sleep bit, in a display.

Slide 7: Sending One Page

oled_flush() sets a window, then pours bytes into it:

const uint8_t win[6] = {0x21, 0, OLED_W - 1, 0x22, (uint8_t)p, (uint8_t)p};
int rc = command(win, sizeof win);
if (rc == 0) { rc = i2c_write_read(OLED_ADDR, fb[p], 1u + OLED_W, 0, 0); }

0x21 sets the column range, 0x22 the page range. In horizontal addressing
mode the SSD1306 advances its own pointer after every data byte, so 128 bytes
land in 128 columns without another address.

The two I2C1->CR2 values that carry it (lesson 09, slide 8) — 7 command
bytes, then 129 data bytes, each with AUTOEND:

SADD = 0x3C << 1 = 0x78; NBYTES = 7, then 129 (0x81). NBYTES is 8
bits wide, so 255 bytes is the most one transfer can carry — a 129-byte page
fits, a whole 1 024-byte screen would not.

Slide 8: The Bus Budget — Arithmetic Before Code

An I²C byte is 9 clock periods (8 bits and the ACK). At 400 kHz, 22.5 µs.

pixels: address + 40 + 1281301 170 + START/STOP2.93 ms
one page1383.12 ms
all 8 pages1 10424.9 ms

The frame budget at 50 updates per second is 20 ms. A full repaint does not
fit — before the game has computed anything, and with the CPU spinning on
TXIS for all of it, because i2c.c is polled.

The AVR edition hit the same wall from the other side: its KS0108 panel had an
8-bit parallel bus at 14 µs a byte, 14.3 ms for a full screen. Serial is
cheaper in pins and dearer in time. Same answer in both editions: do not
send what did not change.

These numbers are a model; the board measures the real one. $PERF's
flush_us field is that measurement (slide 14), and the real TIMINGR clock
is not exactly 400 kHz.

Slide 9: The Framebuffer and Dirty Pages

Three rules, all in oled.c:

  1. Drawing is free on the bus. Every call edits fb in RAM.
  2. A page is dirty only if a byte in it actually changed (slide 4's last line).
  3. oled_flush() sends dirty pages only, and clears each bit once its page is sent. A page whose transfer failed stays dirty and is retried next time.

oled_clear() follows rule 2 too: it marks a page dirty only if the page had
something in it, so clearing a blank screen costs nothing.

The RAM bought for this is 1 032 bytes (8 × 129) — 8 % of the C031's
12 KB. On the AVR edition's ATmega128 the same framebuffer was a quarter of all
its memory.

Slide 10: The Trap — Clear, Then Redraw Everything

The simplest way to draw a frame is oled_clear(), then draw every object.
The picture comes out identical. The bus cost does not:

StrategyPages dirty per SNAKE frame
clear + redraw everythingevery page anything is drawn on — the wall alone is in all 7 below the HUD. Measured on the host: 970 B per frame, 88 % of a full repaint
erase what moved, draw what movedthe new head, the old tail, maybe an apple: 1–3 pages. Measured: 129 B per frame

Clearing changes every lit byte to 0, redrawing changes it back — two real
changes, so the page is dirty even though it ends up the same. Rule 2 cannot
see that the net effect was nothing.

So every game here keeps the positions it last drew and, each frame,
erases those, then draws the new ones. SNAKE goes further and keeps a list of
the cells that changed:

static void mark(int c)
{
    if (n_changed < 8) { changed[n_changed++] = (uint16_t)c; }
    else               { need_full = 1; }     /* too many: repaint all */
}

Rule of thumb for any frame-based display: erase everything that moved, then
draw everything that moves. In that order an erase never cuts into something
drawn this frame.

Slide 12: The Game Loop — Update at a Fixed Rate, Render When Time Allows

Main.c's loop, with the stopwatch lines left out:

while ((int32_t)(ms - next) >= 0) {
    pad_read(&pad);
    if (pad.pressed & PAD_SEL) { full_repaint ^= 1; }
    arcade_step(&pad);
    updates++;
    next += TICK_MS;
    if (++ran == MAX_CATCHUP) {           /* hopelessly behind: give up */
        next = ms + TICK_MS;              /* the lost time, rather than */
        break;                            /* spiral into catching up    */
    }
}
if (ran == 0) {               /* nothing due: sleep until the next tick */
    __WFI();
    continue;
}
sound_poll(ms);               /* start any effect the update asked for */
arcade_draw();                /* RENDER: once, however many updates ran */
if (full_repaint) { oled_invalidate(); }
oled_flush();

A slow frame does not slow the game; it makes the next frame run two updates.
Game speed is set by next += TICK_MS, picture smoothness by how long a
render takes — two different numbers, deliberately decoupled.

Slide 13: Why a Fixed Step — and the Spiral of Death

The alternative, "measure how long the last frame took and move everything
by speed × dt", makes the game depend on the frame time: a slow flush means a
big step, a ball that jumps through a brick, physics that differs between your
board and your neighbour's. A fixed step makes every update identical, which is
what makes the host test possible: same seed, same inputs, same pixels,
checked by hashing the framebuffer.

MAX_CATCHUP is the guard every fixed-step loop needs. If updates ever cost
more than 20 ms, catching up would take longer than the time it is catching up
on, and the loop would never render again — the spiral of death. After 4
updates in a row the loop gives up the lost time instead: the game slows down
rather than freezing.

Measured on the host — Main.c's loop run against a simulated clock, each
frame costing its modelled bus time:

Updates stay at 50 per second in every case. Only the picture rate moves.
These are $PERF's fps and ups fields — the first two numbers to check on
the board.

Slide 14: A Microsecond Stopwatch, Free, From SysTick

This lesson owns SysTick itself — one interrupt a millisecond:

Between interrupts VAL counts down from 47 999 at 48 MHz, so
(LOAD − VAL) / 48 is the microseconds since the last tick:

static uint32_t now_us(void)
{
    uint32_t m, v;
    do {                     /* ms ticked while we read VAL? again */
        m = ms;
        v = SysTick->VAL;
    } while (m != ms);
    return m * 1000u + (SysTick->LOAD - v) / (SystemCoreClock / 1000000u);
}

The loop is lesson 03's torn read: ms and VAL are two values that change
independently, and reading them in the wrong instant pairs a new VAL with an
old ms, 1 ms out. Re-reading until ms holds still fixes it with no
interrupts masked.

The stopwatch times oled_flush() (flush_us, max_us) and the whole frame
(busy %). Once a second:

$PERF,<fps>,<ups>,<flush_us>,<max_us>,<bytes/frame>,<busy %>,<DIRTY|FULL>*CS

Slide 15: One Loop, or the RTOS?

Lesson 07 built a kernel. This lesson does not link it, and that is a decision,
not an oversight.

A game is a single pipeline: nothing can usefully run while the frame is
being computed, and the flush must not overlap the drawing. Splitting it into
tasks buys locking and no parallelism.

The RTOS earns its place when deadlines differ. A drone reads its IMU and
runs its attitude loop hundreds of times a second, and might show status on
this same OLED a few times a second — and a 25 ms flush must not delay the
motors. There the display belongs in a low-priority task, exactly as lesson 09
put its shell at the bottom.

Slide 16: Input — Levels, Edges and Zones

pad_read() returns three views of the buttons (lesson 05's debouncer, two
samples must agree):

p->pressed  = (uint8_t)(now & ~stable);   /* went down since the last read */
p->released = (uint8_t)(stable & ~now);   /* came up                       */
p->down     = now;                        /* held                          */

Games choose the view that fits the action:

ActionUsesWhy
FLAP's flappressedholding the button must not flap 50 times a second
BREAKOUT's servepressed
SNAKE's steeringstick level, larger axis past 35 %a held direction is a held intention
menu up / downstick zone edgecrossing ±50 % once = one step

The stick is two ADC channels scaled to −100…100 with a dead zone, so a released
stick reads exactly 0. Wokwi's joystick reads 0 V at the right (its
documentation says so); pad.c flips it, so x > 0 is always right.

Edges are only as good as the sampling: pressed is set for one call of
pad_read(). That is why the loop reads the pad inside the update loop — once
per tick, never skipped — and not once per frame.

Slide 17: Sprites — and Why const Is Enough on ARM

FLAP's bird is two 8 × 6 frames in the panel's own format — one byte per

static const uint8_t bird[2][BIRD_W] = {

Slide 18: Physics in Two Lines — and Fixed Point

FLAP, every tick (positions and speeds in 1/256 px):

vy += GRAVITY;          /* 28/256 px per tick^2   = 273 px/s^2 */
by += vy;               /* a flap SETS vy = -400  = -78 px/s   */

That is Euler integration: velocity integrates acceleration, position
integrates velocity. Lesson 13's drone altitude is these two lines with a motor
instead of a button.

Measured on the host, and predicted by hand first: with no input the bird
hovers until tick 150, then falls 28·n(n+1)/2/256 px in n ticks. It hits
the ground (27 px below) when n(n+1) ≥ 494, so n = 22 — tick 171. The
test asserts exactly 171. A model you can predict is a model you can test.

Why fixed point bites — a bug the host test found in this lesson. The
paddle first moved px += in->x * 4 / 100 in whole pixels. For any stick under
25 %, x * 4 / 100 is 0: a gentle push did nothing. The autopilot kept
missing balls three pixels from the paddle. The fix keeps the paddle in 1/256
px too:

pxf += (int32_t)in->x * (4 << FP) / 100;    /* in 1/256 px */
px   = (int)(pxf >> FP);

Integer maths has no rounding errors — it has truncation errors, and they
are always towards zero.

Slide 19: Collision — Four Comparisons

static inline int aabb(int ax, int ay, int aw, int ah,
                       int bx, int by, int bw, int bh)
{
    return ax < bx + bw && bx < ax + aw && ay < by + bh && by < ay + ah;
}

Two axis-aligned bounding boxes overlap unless one is entirely left of,
right of, above or below the other. Every collision in the arcade is this one
function — ball and brick, ball and paddle, bird and pipe.

Making it feel right is the craft:

  • FLAP shrinks the bird's box by a pixel all round. A hit you can see is fair; a hit on a corner pixel feels like a bug.
  • BREAKOUT decides the bounce from where the ball was. If it already overlapped the brick's columns a tick ago it came through the top or bottom (flip vy); otherwise through a side (flip vx).
  • Where the ball meets the paddle sets its angle — the centre sends it straight up, the ends at 45°. It is the only control the player has.
  • No tunnelling: one step must be smaller than the thinnest thing it can hit. Bricks are 3 px, the paddle 2 px, the ball 2 px, so the ball's speed is capped below 3 px per tick.

Slide 20: Randomness You Can Replay — xorshift32

uint32_t rng_next(void)
{
    uint32_t x = rng_state;
    x ^= x << 13;
    x ^= x >> 17;
    x ^= x << 5;
    return rng_state = x;
}
uint32_t rng_below(uint32_t n) { return ((rng_next() >> 16) * n) >> 16; }

Marsaglia's xorshift: three shifts, three XORs, a period of 2³² − 1, and no
divide anywhere — rng_below scales with one MULS instead of %, which on
the M0+ would be a library call. The AVR edition used the 16-bit version
(shifts 7, 9, 8), period 65 535.

Deterministic on purpose. The arcade seeds it with the tick on which you
pressed A. You cannot hit the same 20 ms tick twice, so every game is new; a
test that presses A on a scripted tick gets the same game every time.
Measured on the host: same seed → the same 2 934 ticks, score and
framebuffer hash; a different seed → apples elsewhere.

Not for secrets: anyone who sees a few outputs can predict the rest. For where
an apple goes, it is perfect.

Slide 21: Sound — a Sequencer on a Timer

beep.c is lesson 06's PWM pointed at a buzzer: TIM3 at 1 MHz, ARR + 1 =
10⁶ / Hz sets the pitch, CCR1 = half of it makes a square wave. The hardware
keeps the tone going with no CPU — 440 Hz is ARR = 2272.

An effect is a short list of {Hz, ms}, and 0 Hz is a rest:

static const note_t T_EAT[]    = {{1200, 25}, {1600, 25}, {0, 0}};
static const note_t T_OVER[]   = {{392, 150}, {0, 30}, {330, 150}, {0, 30},
                                  {262, 300}, {0, 0}};
static const note_t T_HIGH[]   = {{523, 80}, {659, 80}, {784, 80}, {1047, 80},
                                  {0, 40}, {1047, 200}, {0, 0}};

sound_poll() runs every pass of the loop and starts the next note when the
last one has ended. A game only ever says sfx(SFX_EAT); it has no idea a
timer exists — on the host the same call increments a counter, and the test
asserts the counts (an apple eaten is an SFX_EAT).

One honest limit: the loop polls, so during a 25 ms full flush a note can
overrun by up to 25 ms. Nobody hears it. An interrupt-driven sequencer would
fix it — at the cost of sharing playing with an ISR (lesson 03 again).

Slide 22: SNAKE

Rendered on the host from the real game code — tick 2000 of the autopilot.

The body is a ring buffer of cell numbers (cy × 31 + cx): moving is push
a head, pop a tail, O(1) however long it grows. A bitmap, one bit per
cell, answers "is this snake?" in one test, so biting yourself is not a walk
along the body. 403 cells: 806 B of ring + 51 B of bitmap.

The bite test allows one cell of the body: the tail, which moves out of the
way on the same tick (unless the snake is growing). An early draft popped the
tail before testing, so a fatal move had already shortened the snake — the
host test's "length = 3 + 2 × apples" check caught it, one cell out.

Every fifth apple shortens the move period by a tick; the knob sets where it
starts (8 ticks per move at level 1, 4 at level 5).

Measured on the host, level 3: the autopilot ate 42 apples in 58.7 s,
length 87 = 3 + 2 × 42, score 126 = 3 × 42. With no input the snake
hits the wall on tick 126 — predicted 21 moves × 6 ticks.

Slide 23: BREAKOUT

Rendered on the host from the real game code — tick 900 of the autopilot.

48 bricks are four 16-bit words: bit c of rows[r] is the brick in row
r, column c. Break one with an AND, test "all gone" with four compares.
Top rows pay more; higher levels pay more and give you a narrower paddle
(20 px at level 1, 12 at level 5). Clear a wave and the next is faster.

Measured on the host, level 3: the autopilot (it predicts where the ball
will land) played the full 5 minutes — 188 bricks, 3 waves, score 1 395,
no ball lost. With no input, the ball serves itself after 3 s and the game
ends on tick 599 after three misses.

Slide 24: FLAP

Rendered on the host from the real game code — tick 700 of the autopilot.

Three pipes, recycled: one that leaves on the left reappears 156 px to the
right with a new random gap. The gap shrinks with the level (26 px at level 1,
18 at 5) and the pace rises a little every 5 pipes.

Measured on the host, level 3: the autopilot passed 97 pipes in 71 s
before it clipped one. Its rule: flap when the bird's feet are within 3 px of
the bottom of the gap. Its first rule — flap below the gap's middle — scored
20: a flap climbs ~11 px, and from the middle that hits the top pipe. Physics
first, then tactics.

Slide 25: The Arcade — a State Machine

Rendered on the host from the real game code — game over after the
autopilot's SNAKE, a new high score, NEW HIGH! mid-blink.

OVER ignores buttons for 0.75 s, so the frantic press that lost the game does
not also skip its score. NEW HIGH! blinks by drawing itself with XOR:
drawing it twice restores the pixels, so nothing about the screen has to be
remembered.

Slide 26: $SCORE — a Class Leaderboard With a Checksum

Every finished game prints one line, built by score_frame() with lesson 08's
proto_checksum():

$SCORE,SNAKE,172*2E

host/leaderboard.py reads players' pasted lines (one file per player),
drops any line whose checksum is wrong, and prints the top ten per game.
Measured on the host: the frame the test game produced passes
proto_check(); the same line with one digit changed, $SCORE,SNAKE,9*2A,
fails it.

What the checksum does and does not do:

Two hex digits detect accidents, not intent. Stopping a cheat needs a
secret only the board knows — a message authentication code — and then you
are designing a security protocol. Lab Part 7 is a challenge with honest
players.

Slide 27: What the Host Test Proves

host/run.sh (or run.bat) compiles the five game files and _lib/oled.c and

Slide 29: What Was Measured — and What Could Not Be

Measured on the host, with the real game and display code:

  • every game played for minutes by an autopilot, and ended at a predicted tick with no input;
  • the bytes oled_flush() puts on the bus per frame, dirty vs full: SNAKE 129 B, BREAKOUT 220 B, FLAP 935 B, full 1 104 B;
  • bus time from a 400 kHz model: 24.92 ms for a full frame, 3.1 ms a page;
  • the loop against a simulated clock: 50 updates/s always, 40.1 fps when every frame is a full repaint;
  • the $SCORE frame's checksum, the high score, the screenshots.

Not measured, because nothing here ran in Wokwi:

  • the real flush time — i2c.c is polled and its TIMINGR is not exactly 400 kHz; $PERF's flush_us will say;
  • whether Wokwi's SSD1306 accepts the init sequence and the 129-byte page writes (it documents support for Adafruit's library, which sends the same commands);
  • CPU time of update and draw (busy % minus the flush);
  • whether the keys a and b reach the buttons while the joystick has focus;
  • whether it is fun at level 3.

Slide 30: What Carries Forward

  • Pure C core, thin platform. Part 3's control_step() contract is this split: the controller is pure C, Main.c is the hardware, and a PC runs the controller against physics before any motor turns.
  • Fixed timestep. A drone's attitude loop is next += period with a deadline that matters more than a frame rate; the RTOS version of the same line is lesson 07's os_delay_until().
  • Euler integration in fixed point is the drone's altitude and the robot's odometry.
  • The bus budget. The app board's MPU6050 sits on these same two wires. A 25 ms flush in the middle of a control loop would freeze it — so a display there belongs in a low-priority task that sends a dirty page at a time.
  • DMA. Lesson 10 moves a transfer like this one off the CPU entirely: start it, do something else, take one interrupt at the end.
