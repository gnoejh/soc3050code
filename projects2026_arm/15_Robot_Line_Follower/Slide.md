# Robot Line Follower: A Robot That Lives Inside the Chip
## SOC3050 ARM Edition — Part 3, Applications

**Reference**: [STM32 Reference Manual](https://www.st.com/resource/en/reference_manual/rm0490-stm32c0x1-advanced-armbased-32bit-mcus-stmicroelectronics.pdf) ·
**Board manual**: [UM2953, STM32 Nucleo-64 boards (MB1717)](https://www.st.com/resource/en/user_manual/um2953-stm32c0-nucleo64-board-mb1717-stmicroelectronics.pdf)

**A robot races laps of a taped track on the OLED. Turn the knob up and it
goes faster — until a corner throws it off the line.**

There is no robot. Its motors, its tyres, its seven light sensors and the
track itself are a **world task** inside the same firmware, running at the
top priority, 200 times a second. Your controller is a separate task that
sees only what a real line follower would see — seven numbers and two
encoder counts — and answers with two wheel speeds. That split is
**Software-In-The-Loop**, and it is how the drone and robot lessons that
follow are all built.

Figures marked **measured on the host** come from `host/sitl.c`, which races
the very same `world.c` and `control.c` on a PC. Nothing in this deck has yet
been watched running in Wokwi; slide 27 says exactly what that leaves open.

## The Board: This Lesson's Pins

Before any register, find the pins. Every highlighted dot is a header pin that
this lesson's `diagram.json` wires something to — the same circuit you paste
into Wokwi — at its position on the Nucleo-C031C6, to scale. A label reads
*MCU pin (header name, if different)* and what the pin does here.

The two outer double rows are ST's **morpho** headers, which reach every pin
of the chip; the two inner single rows are the **Arduino**-compatible header
(A0–A5 on the left, D0–D15 on the right). Some MCU pins appear on both — PA5 is
also `D13` — so the highlighted position is the one this lesson's wire uses.
The real board's headers are drawn in its manual, UM2953 (top bar).

position in its port's registers**. Pin *n* of GPIOA is bit *n* of
`GPIOA->IDR`, bits 2*n*+1 : 2*n* of `GPIOA->MODER`, and so on (lesson 05,
slide 4). Each cell below is one pin, drawn in register order, marked with how
this lesson configures it.

## Slide 3: The Contract — `control.h`

```c
typedef struct {
    /* line[i]: reflectance 0..1000 - 1000 is black tape, ~100 is white floor.
     * i = 0 is the RIGHTMOST sensor, i = 6 the leftmost, looking forward;
     * sensor i sits (i - 3) * 13 mm to the left of the robot's centreline.  */
    uint16_t line[LINE_SENSORS];
    int32_t  enc_left, enc_right;   /* wheel encoder counts since reset         */
    int16_t  knob;                  /* the operator's speed setting, 0..1000    */
    uint32_t t_ms;                  /* time of this reading                     */
} sensors_t;

typedef struct {
    int16_t left, right;            /* wheel speed commands, mm/s, +-2000       */
} actuators_t;

void control_step(const sensors_t *in, actuators_t *out);   /* at 100 Hz    */
```

**Integers at the boundary** — readings arrive as ADC counts, motor drivers
take integer set-points. What happens inside `control_step()` is the
controller's business; this one uses `float` (lesson 10 measured what each
soft-float operation costs on this core).

## Slide 4: Five Tasks, Five Rates

| Task | Prio | Period | Job | Stack (words) |
|---|---|---|---|---|
| `world` | 5 | 5 ms | `world_step()` + `world_sense()` | 160 |
| `control` | 4 | 10 ms | `control_step()`, or the joystick in manual | 160 |
| `ui` | 3 | 20 ms | `pad_read()`, buttons, beeps, `$LINE` at 10 Hz, `$LAP` | 256 |
| `shell` | 2 | on input | `kp ki kd df slow thr`, `noise ambient fail`, `gains`, `stats` | 224 |
| `display` | 1 | 100 ms | the OLED: robot, laps, sensor bar | 256 |

**Rate-monotonic**: the shorter the period, the higher the priority (lesson
07). The world must never be late — a late physics step is a robot that
teleports. The display is the opposite: it gets whatever time is left, and
the I²C driver is polled, so its flush *is* CPU time.

Stacks are sized from `gcc -fstack-usage` plus newlib's printf frames (the
deepest chain is `send_frame()` → `vsnprintf()` → `_svfprintf_r`, ~460 bytes),
then checked live with `stats`. The build: **FLASH 26 920 B, RAM 9 352 B**.

## Slide 6: Model 2 — Motors Have Mass

```c
    float dl = f_clamp((ul - world.wl) * (dt / MOTOR_TAU_S), -MOTOR_ACC_MMS2 * dt, MOTOR_ACC_MMS2 * dt);
    float dr = f_clamp((ur - world.wr) * (dt / MOTOR_TAU_S), -MOTOR_ACC_MMS2 * dt, MOTOR_ACC_MMS2 * dt);
    world.wl += dl;
    world.wr += dr;
```

A first-order lag, **τ = 40 ms**, and a slew limit of **8 m/s²**. Ask for
1000 mm/s from standstill and you get 63% of it after 40 ms — and no faster
than the limit allows.

Why model it? Because a controller tuned against a robot with no lag
**overshoots** a real one. Every lap 1 in the results is ~80 ms slower than
lap 2 for exactly this reason: a standing start.

## Slide 8: Encoders Count Wheels, Not Ground

```c
    /* 4. encoders: what the wheels turned, slip or no slip */
    world.dist_l += world.wl * dt;
    world.dist_r += world.wr * dt;
```

360 ticks per revolution on a 16 mm wheel: **3.58 ticks per mm**. While the
friction circle is saturated the wheels keep turning and the robot slides
sideways, so the encoders report distance the robot never travelled — exactly
as real ones do.

That is why this controller ignores them: odometry is only as good as the
grip. They are in `sensors_t` for Lab Part 8, and for lesson 16, which needs
them to know how far it has gone.

## Slide 10: Finding the Tape Cheaply

The track is up to 111 segments; seven sensors × 111 exact distances, 200
times a second, is ~155 000 distance calculations a second in soft float.
So `cover()` filters first, in integers:

```c
        if (ibx + reach < lox || ibx - reach > hix || iby + reach < loy || iby - reach > hiy) { continue; }
        cand[nc++] = i;
```

A box test per segment against the bar's centre — four compares — and the
exact `track_seg_dist()` only for the handful that pass — **measured on the
host, 2.8 to 3.7 segments per step on average, 6 at most**, out of 70–110.
On the FIGURE-8's
**crossing** both branches pass the test, so every sensor goes dark as the
robot crosses: the physics of the cross line falls out for free.

The judge does the opposite: it searches only **segments near the last
one** (`k = -4 .. 6`), so at the crossing it stays on the branch the robot is
really on. Two searches, two different questions.

## Slide 13: The Judge

```c
    if (world.halfway && world.s < 0.1f * L && world.seg < (track.n - 1) / 2) {
        /* crossed the start line going forward, having been round */
```

- **Progress** `s`: distance along the centreline of the nearest point.
- **A lap** counts only after passing half distance — reversing over the
  start line does not score.
- **DNF, lost**: no sensor over tape for **1 s** (`DNF_WHITE_MS`).
- **DNF, off**: robot centre more than **150 mm** from the line (`DNF_FAR_MM`)
  — cutting across a hairpin to the next straight is not a shortcut.

The judge lives in `world.c` because it uses the truth — where the robot
really is — which the controller is never told.

## Slide 14: Control Step 1 — Where Is the Line?

```c
        float w = (float)in->line[i] - g->thr;
        if (w <= 0.0f) { continue; }
        float y = (float)((i - (LINE_SENSORS - 1) / 2) * SENSOR_PITCH_MM);
        sw  += w;
        swy += w * y;
```

`pos = swy / sw` — the sensor positions, weighted by how much darker than the
threshold each reads. Worked: tape 5 mm left of centre.

| Sensor | y (mm) | distance | reading | weight (− 300) |
|---|---|---|---|---|
| 4 | +13 | 8 mm | 650 | 350 |
| 3 | 0 | 5 mm | 900 | 600 |
| 2 | −13 | 18 mm | 100 | — |

`pos = 350 × 13 / 950 = 4.8 mm`. Seven sensors 13 mm apart resolve a few
millimetres — the subtraction of `thr` is what keeps the white floor from
voting.

## Slide 15: Control Step 2 — PID

```c
    float d_raw = have_prev ? (e - e_prev) / dt : 0.0f;
    d_filt += g->dfilt * (d_raw - d_filt);               /* first-order low-pass */
    ...
    float turn = g->kp * e + g->ki * i_acc + g->kd * d_filt;
```

`left = v − turn`, `right = v + turn`. Defaults: **kp 20, kd 1.0, ki 0,
dfilt 0.5**.

**Why P alone is not enough.** The sensors sit 70 mm ahead of the axle, so
they see the robot's *heading* error early — a free derivative, worth
70 mm ÷ v of lead: 70 ms at 1 m/s, but only 50 ms at 1.4 m/s. Meanwhile the
motors lag 40 ms. Speed up and the free lead shrinks below the lag, and P
alone starts to weave. D puts the lead back.

## Slide 16: Steps 3 and 4 — Speed, and a Lost Line

```c
    float v = base * (1.0f - g->slow * f_clamp(f_abs(e) / HALF_BAR_MM, 0.0f, 1.0f));
```

**Corner slow-down**: a big error usually means a corner, so lose up to half
the speed (`slow 0.5`) as the line drifts to the bar's edge.

```c
        if (f_abs(last_pos) < GAP_POS_MM && lost_ms <= COAST_MS) {
            ctl_state.lost = 1;                         /* a gap: straight on   */
```

**Lost line**: the line was near the middle when it vanished → probably a
**gap**: drive straight for up to 400 ms. It was at an edge → the robot
overshot a corner: **spin toward that side**. And if five or more sensors
are dark at once, it is a **crossing**: hold the last error and keep D and I
out of it.

On HAIRPINS the corner limit is 908 mm/s, yet the robot survives a 1350 mm/s

is both **200 mm/s less brave and 0.65 s slower** per lap. On OVAL and
FIGURE-8 the wheel limit (2000) arrives before the friction limit does.

## Slide 20: Measured — Noise and the D Term

**Measured on the host**: S-BENDS, knob 700. *Chatter* is the RMS change in
`right − left` between control steps: how hard the motors buzz.

| Noise | dfilt 1.0 (none) | dfilt 0.5 | dfilt 0.25 |
|---|---|---|---|
| 0 | 3.81 s, 5.6 mm, **238** | 3.80 s, 5.3 mm, 120 | 3.84 s, 7.2 mm, 100 |
| 15 | 3.80 s, 5.5 mm, 256 | 3.80 s, 5.4 mm, 128 | 3.83 s, 7.2 mm, 103 |
| 80 | 3.82 s, 6.1 mm, **602** | 3.81 s, 5.7 mm, 256 | 3.85 s, 8.5 mm, 162 |

*(best lap, RMS error, chatter mm/s)*

D differentiates noise: at noise 80 unfiltered, the motors are commanded
**2.4× as violently**, for no gain in lap time. A filter halves it — but
filter too hard (0.25) and the RMS error grows by a third to a half, because a filter is a
**delay**, and delay is what D was there to cancel. Even at noise 0 the
chatter is not zero: seven sensors make a staircase, and D sees every step.

## Slide 23: Sharing Without Tearing

```c
        actuators_t a;
        __disable_irq(); a = sh_act; __enable_irq();
```

Every shared struct has **one writer**; readers copy it whole inside a
critical section a few microseconds long — lesson 03's tearing rule. A
half-copied `sensors_t` is a sensor bar that never existed.

Two things need more than that:

- **`track.pt`** is rewritten when you press **B** and read by the display
  while it draws: a **mutex**, `track_lock`. The world task (prio 5) can
  then wait on the display (prio 1) — priority inheritance (lesson 07)
  lends the display priority 5 until it lets go.
- **Resetting the controller** is the control task's job, not the world's:
  the world bumps `run_id`, and the control task calls `control_reset()`
  when it sees it change. One writer, again.

## Slide 24: Measuring on the Chip

The host can race the code but cannot time it — a PC has an FPU. On the
chip, `stats` reports what each step really costs:

```c
static uint32_t cycles_now(void)
{
    uint32_t ms, val;
    do { ms = os_ticks(); val = SysTick->VAL; } while (ms != os_ticks());
    return ms * (SysTick->LOAD + 1u) + (SysTick->LOAD - val);
}
```

```regs
# SysTick as the kernel leaves it: reload 47999 = one 1 ms tick at 48 MHz
LOAD ; SYST_RVR | 32 = 0x0000BB7F | !23:0 RELOAD
VAL ; SYST_CVR, counts DOWN | 32 | !23:0 CURRENT
```

The kernel's millisecond count plus how far `VAL` has counted down gives a
cycle-accurate clock with no extra timer. The loop re-reads if a tick lands
between the two reads. **Budget:** the world step must fit in 240 000 cycles
(5 ms); the expectation is a few percent of that. The number itself has
**not yet been measured** — it is the first thing to read in Wokwi.

## Slide 26: What Each Choice Costs

| Choice | Cost | Saved |
|---|---|---|
| `fmath.h` instead of `sinf`/`cosf` | — | ~4 KB of flash (lesson 10) |
| float world on a no-FPU core | ~50–100 cycles per operation | readable physics |
| integer box filter before exact distances | 4 integer compares per segment | ~97% of the exact distances |
| XOR robot + dirty pages | 11 × 11 bit mask in RAM | ~55% of the I²C traffic |
| stacks from `-fstack-usage` | an hour of reading | 2.4 KB of RAM (11 728 → 9 352 B) |
| `TRACK_MAX_PTS` 128, `int16_t` mm | 1 mm rounding | 768 B vs float points |

The first build linked at **11 728 B of RAM** — 95% of the chip — with
generous guessed stacks. Measuring the deepest call chain in each task cut
that to 9 352 B. Guess stacks and you run out of RAM; measure them, and
then check the guess with `stats`.

- **Stacks.** Sized by analysis; `stats` prints the real high-water marks.
