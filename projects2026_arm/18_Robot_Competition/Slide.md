# Robot Competition: A Sumo Tournament Inside the Chip
## SOC3050 ARM Edition — Part 3, Applications

**Reference**: [STM32 Reference Manual](https://www.st.com/resource/en/reference_manual/rm0490-stm32c0x1-advanced-armbased-32bit-mcus-stmicroelectronics.pdf) ·
**Board manual**: [UM2953, STM32 Nucleo-64 boards (MB1717)](https://www.st.com/resource/en/user_manual/um2953-stm32c0-nucleo64-board-mb1717-stmicroelectronics.pdf)

**Two robots, one ring, and only one of them is written by you.**

A sumo robot has one job: push the other robot out of a 77 cm ring before it
pushes you out. It knows nothing but what three distance sensors, four line
sensors, two wheel encoders and a bump switch tell it — 50 times a second.
This lesson simulates the ring, the motors, the tyres and the sensors **inside
the firmware**, hands each robot's brain only its own sensors, and then runs a
tournament: your `student.c` against five opponents with personalities. The
line it prints at the end is your entry to the class tournament.

Figures marked **measured on the host** come from `host\run.bat`, which
compiles the same physics, referee and strategies with the PC's gcc. Nothing in
this deck has been watched running in Wokwi.

## The Board: This Lesson's Pins

Before any register, find the pins. Every highlighted dot is a header pin that
this lesson's `diagram.json` wires something to — the same circuit you paste
into Wokwi — at its position on the Nucleo-C031C6, to scale. A label reads
*MCU pin (header name, if different)* and what the pin does here.

The two outer double rows are ST's **morpho** headers, which reach every pin
of the chip; the two inner single rows are the **Arduino**-compatible header
(A0–A5 on the left, D0–D15 on the right). Some MCU pins appear on both — PA5 is
also `D13` — so the highlighted position is the one this lesson's wire uses.
The real board's headers are drawn in its manual, UM2953 (top bar).

`GPIOA->IDR`, bits 2*n*+1 : 2*n* of `GPIOA->MODER`, and so on (lesson 05,
slide 4). Each cell below is one pin, drawn in register order, marked with how

## Slide 2: The Rules — Real Mini-Sumo, Simplified

| | Real mini-sumo | This lesson |
|---|---|---|
| ring | 77 cm diameter, black, 2.5 cm white border | `RING_R 0.385f`, `LINE_W 0.025f` |
| robot | 10 × 10 cm, 500 g | a 55 mm-radius disc, `ROBOT_M 0.50f` |
| start | wait **5 s** after the start signal | wait **3 s** (`COUNTDOWN_STEPS 600`) |
| out | any part touches outside the ring | the robot's **centre** leaves the ring |
| round | 3 min, then the judges decide | **20 s**, then a draw |
| match | best of 3 rounds | best of 3: first to 2; equal = drawn match |

Every robot is the **same machine** — same motors, same tyres, same sensors.
The only thing that differs is the brain. That is what makes it a programming
competition and not a budget one.

Start positions come from a **seed**: both robots on a random line through the
centre, 10–20 cm out, face-to-face, side-on, back-to-back or random, ±15°.
Round 2 swaps round 1's places, so neither robot keeps a lucky corner.

## Slide 3: The Contract — `strategy.h`

```c

                   strategy_mem_t *mem);

typedef struct {
    int32_t  t_ms;               /* NEGATIVE during the 3 s countdown        */
    uint16_t dist_mm[N_DIST];    /* to the opponent's surface, or DIST_NONE  */
    uint8_t  edge;               /* EDGE_FL | EDGE_FR | EDGE_BL | EDGE_BR    */

typedef struct { uint32_t w[16]; } strategy_mem_t;       /* 64 bytes     */
```

**In:** only this robot's sensors. No position, no map, no opponent velocity —
a real sumo robot does not know where it is either.
**Out:** two numbers. **Memory:** 64 bytes, zeroed at the start of every round.

## Slide 4: Why the Memory Rule Matters

A strategy may keep state **only** in `*mem`. No globals, no `static`
variables. Three reasons, all of them engineering:

1. **Two copies must be independent.** Student vs student runs the same code
   twice. A `static` counter would be *shared* by both robots.
2. **A match must repeat from its seed.** A global that survives from match 6
   into match 7 makes match 7's result depend on history — and the referee can
   no longer re-run it to check a claim.
3. **The budget is real.** 64 bytes × 2 robots is what this design can afford;
   a contract with a hard size is how embedded teams share one RAM.

```c
typedef struct { uint8_t mode; int16_t timer; } my_state_t;
STRATEGY_STATE_FITS(my_state_t);           /* _Static_assert: a COMPILE error if > 64 */
my_state_t *s = STRATEGY_STATE(my_state_t, mem);
```

The host league enforces rule 1–2 mechanically: `nm` on your object file, and
any `B b D d C` symbol is a rejection (slide 24).

## Slide 6: Model — a Motor Is a Line, a Tyre Is a Ceiling

A DC motor's force falls linearly with speed: full force at stall, zero at its
no-load speed. A tyre can only pass on so much of it — μN — before it slips.

```c
float f = F_STALL * (drive - v_ground / V_MAX);     /* the motor's line   */
if (f > grip || f < -grip) {                        /* more than the tyre */
    f = f > 0.0f ? grip : -grip;                    /* can hold: it slips */
    v_wheel = V_MAX * (drive - f / F_STALL);        /* and spins          */
}
*enc += v_wheel * DT;                               /* the ENCODER sees it */
```

`F_STALL` = 3.0 N per wheel; grip = μ · mg/2 = 1.0 × 0.5 × 9.81 / 2 = **2.45 N**.
So a standing start is **traction-limited**: the wheels slip until the motor
line falls under the ceiling at v₁ = 0.146 m/s, then the robot approaches
0.8 m/s with τ = mV/(2F) = 67 ms.

| Full throttle from rest | Model (closed form) | **Measured on the host** |
|---|---|---|
| top speed | 0.800 m/s | **0.800 m/s** |
| time to half speed | 47.7 ms | **50.0 ms** (one 5 ms step) |
| wheels slip at launch | yes | **yes** |

Checking the simulator against its own equation is the cheapest test there is.

## Slide 8: Model — Two Discs Collide

```c
float vn = rvx * nx + rvy * ny;               /* closing speed along the normal */
if (vn < 0.0f) {
    float jn = -(1.0f + RESTITUTION) * vn / (2.0f / ROBOT_M);   /* stop closing */
    ...
    float jt = f_clamp(-vt / k, -MU_BODY * jn, MU_BODY * jn);   /* Coulomb      */
    a->w -= ROBOT_R * jt / ROBOT_I;            /* a glancing hit spins them     */
}
/* then split any overlap between them */
```

- **Normal impulse**: the bodies stop approaching (`RESTITUTION 0.1f`: almost
  dead, like rubber-tyred robots).
- **Friction impulse**: along the surface, at most μ·jn — a glancing blow turns
  the other robot.
- **Pushing is emergent.** Nothing says "A pushes B". A's motor accelerates A
  into B every step, the impulse shares the velocity, and B's tyres resist.
  The force balance on slide 7 falls out of these lines.

The cost of a disc: no wedge, no scoop, no corners. Real sumo robots win with
low wedges that lift the opponent's wheels off the ground. A disc keeps the
physics on one slide.

## Slide 10: Sensors — the Line, and the Speed That Jumps It

Four reflectance sensors at the corners, (±40, ±40) mm. They read **white only
on the border band**, `RING_R − LINE_W ≤ r ≤ RING_R`:

```c
/* White only ON the border.  Past RING_R there is no dohyo under the
 * sensor and it reads like black - a robot fast enough to cross the
 * line between two reads never sees it. */
if (r2 >= in2 && r2 <= out2) { bits |= (uint8_t)(1u << k); }
```

The arithmetic every sumo team does:

| | |
|---|---|
| border width | 25 mm |
| top speed | 0.8 m/s = **16 mm per 20 ms call** |
| reads that land on the 25 mm band, crossing it at top speed | **1 or 2** |
| reads that land on it at half speed | 3 or 4 |

At 50 Hz the line is wide enough — **if you act on the first read**. A
strategy that needs two reads to agree, or waits to finish a manoeuvre, drives
straight out. Lab Part 2 counts how often the starter does (`s-out` in the
league table).

## Slide 11: Sensors — Encoders Measure the Wheel

`enc_l`, `enc_r` count wheel travel in mm. When the tyre slips, **the wheel
turns and the robot does not** — exactly what a real optical encoder on the
motor shaft reports.

| Situation | Encoders say | The robot |
|---|---|---|
| cruising | ≈ `V_MAX × drive × t` | moves that far |
| launch at 100 % | more than it moved | wheels spin for 15 ms |
| nose-to-nose stalemate at 100 % | ~0 | stalled, motors at full force |
| being pushed backwards while driving forward | forwards, fast | goes backwards |

So encoders cannot give position in a fight. They *can* tell you "I am
commanding forward and my wheels have stopped" — a stall: you are in a pushing
match. Combine with `BUMP_FRONT` and you know who you are pushing.

## Slide 12: Sensors — the Bump Switch

```c
static uint8_t bump_side(const body_t *b, float nx, float ny)
{
    float lx =  nx * c + ny * s;                        /* in the robot frame */
    float ly = -nx * s + ny * c;
    if (lx >  0.7071f) { return BUMP_FRONT; }           /* within 45 deg      */
    if (lx < -0.7071f) { return BUMP_BACK; }
    return ly > 0.0f ? BUMP_LEFT : BUMP_RIGHT;
}
```

Set by any contact since the robot's last call, cleared when read. It is the
one sensor that says **where you are being hit** — and slide 7 says a hit on
`BUMP_LEFT` or `BUMP_RIGHT` is the dangerous one. Turn the nose to it.

## Slide 13: The Referee — Everyone Senses the Same Instant

```c
for (int i = 0; i < 2; i++) { world_sense(&m->w, i, &m->view[i]); ... }  /* sense both */
for (int i = 0; i < 2; i++) { m->e[i]->fn(&m->view[i], &m->cmd[i], &m->mem[i]); } /* think both */
for (int i = 0; i < 2; i++) { world_drive(&m->w, i, ...); }                /* latch both */
```

If robot 0 sensed, thought and *moved*, and only then robot 1 sensed, robot 1
would see 20 ms into robot 0's future — and whichever brain happened to be
"robot 1" would win more. Same-instant sensing is what a real match gives you
(both robots run in parallel), and it costs one extra loop.

The tournament also **alternates sides**: the student is robot 0 in even
matches and robot 1 in odd ones (`tour_student_side(k)`).

## Slide 14: Two Rates

| Loop | Period | Who | Why that rate |
|---|---|---|---|
| physics | **5 ms** (`DT`) | `world_step()` | contact needs small steps: at 0.8 m/s a robot moves 4 mm |
| control | **20 ms** (`STEPS_PER_CTRL 4`) | `strategy_step()` | a typical hobby sumo loop; 16 mm per call at top speed |
| display | 80 ms | `task_oled` | an OLED frame is ~1 KB, ~25 ms of I²C |
| buttons | 20 ms | `pad_read()` | lesson 05's debouncer, two-sample window |

The physics runs four times per brain call. A controller that sees the world
less often than the world changes is *normal* — it is what "sample rate" means,
and slide 10 is what it costs.

## Slide 15: Determinism — the Property the Tournament Stands On

A match must come out **bit-for-bit identical** from its seed — on the chip,
on a PC, today and next week. What that takes:

- **one random generator per purpose**, seeded from the match seed: the
  referee's (start positions) and each robot's (sensor noise); `xorshift32`, 3
  shifts and 3 XORs, identical everywhere;
- **noise drawn on every read**, seen or not — so the *sequence* never depends
  on what happened;
- **no state outside the match**: strategies' 64 bytes zeroed each round;
- **IEEE single-precision floats, no fused multiply-add**: `-ffp-contract=off`
  on the PC; the M0+'s soft-float has no FMA to fuse into.

| **Measured on the host** | |
|---|---|
| whole league (1500 matches) twice, same seed | **4C26E6F2** both times |
| the next seed instead | `B9662C8B` — different |
| built at `-O0`, `-O2`, `-Os` | **identical** league and tournament hashes |

**Not measured:** that the chip's soft-float matches the PC's SSE bit for bit.
It should — both round every operation to nearest-even — and the `$RESULT`
hash is how you find out (Lab Part 1).

## Slide 17: Measure — Counting Cycles on a Chip With No Cycle Counter

Cortex-M3 and up have `DWT->CYCCNT`. The M0+ does not: `core_cm0plus.h`
defines no DWT at all. But the kernel's SysTick already counts 48 MHz cycles:

```regs
# The kernel's SysTick: RELOAD = 47 999, one interrupt per ms
LOAD ; SYST_RVR | 32 = 0x0000BB7F | !23:0 RELOAD
VAL ; SYST_CVR, counts DOWN | 32 | !23:0 CURRENT
ICSR ; SCB | 32 | 31 NMIPENDSET, 28 PENDSVSET, 27 PENDSVCLR, !26 PENDSTSET, 25 PENDSTCLR, 23 ISRPREEMPT, 22 ISRPENDING, 17:12 VECTPENDING, 5:0 VECTACTIVE
```

```c
__disable_irq();
uint32_t t = os_ticks();
uint32_t v = SysTick->VAL;
uint32_t pend = SCB->ICSR & SCB_ICSR_PENDSTSET_Msk;
__enable_irq();
if (pend && v > load / 2u) { t++; }      /* wrapped, not yet counted */
return t * (load + 1u) + (load - v);
```

`cycles = ticks × 48 000 + (47 999 − VAL)`. The one trap: VAL has wrapped to
47 999 but the interrupt has not counted it yet — then a measurement is 48 000
cycles too *small*. With interrupts off, `PENDSTSET` says exactly that.

## Slide 18: The Time Budget — 20 000 Cycles

`STEP_BUDGET 20000u`: **417 µs** per `strategy_step()` call, measured around
every call by the referee (`m->clock`):

```c
uint32_t t0 = m->clock();
m->e[i]->fn(&m->view[i], &m->cmd[i], &m->mem[i]);
uint32_t c = m->clock() - t0;
if (c > m->cyc_max[i]) { m->cyc_max[i] = c; }
```

Why a budget at all? A real sumo robot's 50 Hz loop also has to read sensors,
run motor PWM, and talk — the strategy gets a slice. Here, every soft-float
operation costs ~50–100 cycles (lesson 10), so 20 000 cycles is a few hundred
float operations: plenty for a state machine, not enough for a search.

The worst call goes into `$RESULT`; **an entry over budget is rejected**. The
worst case — not the average — because a robot that misses one deadline in
a hundred misses the one that mattered.

## Slide 19: The Knob Is the Clock Rate

| Knob (`pad.knob`, 0..1000) | Match steps per 20 ms tick | Means |
|---|---|---|
| 0–199 | 4 | x1: real time |
| 200–399, 400–599 | 8, 16 | x2, x4 |
| 600–799 | 32 | x8 |
| 800–1000 | as many as fit in 14 ms | MAX (silent: no beeps) |

```c
uint32_t budget = speed ? 4u * speed : 100000u;
for (uint32_t n = 0; n < budget; n++) {
    if (os_ticks() - now >= 14u) { break; }
    ...
```

The 14 ms cap is the design decision: **if the CPU cannot keep up with x8, the
match slows down — it never skips steps**, because skipped steps would change
the result. `stats` prints the achieved speed. The other 6 ms of each tick are
what keeps the shell and the OLED alive.

How fast *is* one step on this chip? Not measured yet — `stats` prints the mean
and worst `match_step()` in cycles. That is Lab Part 1's first number.

## Slide 20: Flash Is the Scarce Resource

| Build | FLASH | of 32 KB |
|---|---|---|
| first draft, shell parsed with `sscanf()` | 30 068 B | 92 % — over the 29 KB line |
| `sscanf()` replaced by an 11-line `number()` | 27 392 B | |
| `fmath.h`'s `f_sin`/`f_cos` called through one out-of-line copy | **27 056 B** | 83 % |

`sscanf` dragged in `_scanf_i`, `__ssvfscanf_r` and `strtol`/`strtoul` —
**2.7 KB for parsing two numbers**. `fmath.h`'s functions are `static inline`,
so each call site got its own polynomial; one out-of-line copy saved 0.5 KB
with **bit-identical results** (the host hash did not change).

RAM: **9 608 B** of 12 KB — three task stacks (512 + 384 + 384 words), the
OLED's 1 KB framebuffer, the match.

What is left — about 2 KB under the line — is **your** `student.c`'s budget.

## Slide 24: Submitting — and Why Cheating Does Not Pay

```
$RESULT,<name>,<W>,<D>,<L>,<hash>,<max cycles>,<build>*CS
```

| Field | Catches |
|---|---|
| `*CS` | a line edited by hand — lesson 08's NMEA XOR checksum |
| `<hash>` | FNV-1a over every round's winner, end step and final positions; the TA re-runs **your** `student.c` on the host with the same seed and must get the same hash |
| `<max cycles>` | a strategy over the 20 000-cycle budget |
| `<build>` | FNV-1a of every flash byte: which exact firmware produced the line |

And copy-paste? **Two students with the same strategy get the same hash** —
the hash is the behaviour, not the name.

On the host, `run.bat` compiles each file with
`-DSTRATEGY_PREFIX=<file name>` and checks it with `nm`:

```
0000000000000000 b calls.0
REJECT host\strategies\cheater.c: the symbols above are variables outside strategy_mem_t
```

## Slide 25: The Host League — Thirty Files, One Program

Everyone writes `strategy_step`. How do 30 of them link together?

```c
/* strategy.h */
#define strategy_step STRATEGY_CAT(STRATEGY_PREFIX, _step)   /* -> alice_step */
#define strategy_name STRATEGY_CAT(STRATEGY_PREFIX, _name)

/* host/register.h, force-included with gcc -include */
__attribute__((constructor))
static void STRATEGY_CAT(STRATEGY_PREFIX, _register)(void)
{
    league_register(REG_STR(STRATEGY_PREFIX), strategy_step);
}
```

The **macro** renames each file's function after its file name; the
**constructor** — a function the C runtime calls before `main()` — hands it to
the league. Nobody edits a list, and the league sorts entries by name so link
order cannot change a result.

```
host\run.bat strategies\alice.c strategies\bob.c
```

## Slide 27: What Carries Forward

- **Contracts make teams.** `strategy_step()` is lesson 12's game loop and
  Part 3's `control_step()` in miniature: a fixed interface, a fixed budget,
  fixed memory. Whoever is on the other side can be swapped — a bot, a
  joystick, a classmate.
- **Simulate the plant, keep the controller real.** The brains here are the
  C that would drive a real mini-sumo robot; only `world.c` would go.
- **Determinism is a feature you build.** One RNG per purpose, no hidden state,
  same-instant sensing, no FMA. Without it, no result in this lesson could be
  checked.
- **Lesson 19 is yours.** The final project starts from everything here: an
  RTOS, a display, a simulated world, a measured budget — and a way to prove
  what your code did.
